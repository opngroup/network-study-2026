# 과제 B 메모 — 와이어샤크로 본 TCP 연결 한 번 (11/2)

## 무엇을 잡았나

- 서버: `week-01/이주영/assignment-a/_ref/step5_threads.py` (`127.0.0.1:9000`)
- 클라이언트: `nc 127.0.0.1 9000` → `hello` → Ctrl+C
- 인터페이스: `Loopback: lo0` · 화면 필터: `tcp.port == 9000`

## 12줄 = 네 장면

| 장면 | 패킷 | Info |
| --- | --- | --- |
| ① 연결 (3-way handshake) | 3개 | `SYN` → `SYN, ACK` → `ACK` |
| ①-덤 | 1개 | `TCP Window Update` |
| ② hello 보내고 에코 받기 | 4개 | `PSH, ACK` → `ACK` → `PSH, ACK` → `ACK` |
| ③ 끊기 (4-way) | 4개 | `FIN, ACK` → `ACK` → `FIN, ACK` → `ACK` |

- 시각(Time)을 보면 사람이 보인다: 연결 77초 → hello 101초 → Ctrl+C 128초. 그 사이 패킷이 하나도 없다 — 연결이 열려 있어도 할 말이 없으면 조용하다
- 방향은 포트로 읽는다: `60356 → 9000` 은 nc → 서버, `9000 → 60356` 은 서버 → nc. 60356 은 OS 가 붙인 임시 포트(1주차)

## 이해한 것

### Info 열 ≠ TCP 헤더 그대로

- 포트·플래그·Window·옵션은 헤더에 있는 값
- `Seq=0` 은 와이어샤크가 0 부터 다시 센 **상대 순번**. 진짜 헤더에는 큰 무작위 수(`Sequence Number (raw)`)
- `Len`, `[TCP Window Update]` 는 와이어샤크의 **계산·해석**이다
- 진짜 헤더는 패킷을 클릭하고 아래 `Transmission Control Protocol` 을 펼쳐서 본다. IP 는 그 위 `Internet Protocol Version 4` 에 있다

### MSS 와 Window

- **MSS** = 상자 하나의 최대 크기. SYN 때 한 번만 알려 준다
  - 루프백 MTU 16384 − IP 헤더 20 − TCP 헤더 20 = **16344** (캡처의 `MSS=16344` 와 일치)
  - Wi-Fi(`en0`) MTU 는 1500 → 인터넷 서버와는 MSS 가 보통 1460 근처
- **Window** = 받는 쪽 창고의 빈 자리. "확인 안 기다리고 여기까지는 보내도 돼". 패킷마다 바뀐다(흐름 제어)

### Window Scale (`WS=64`)

- 헤더의 Window 칸은 16비트 → 최대 65535
- SYN 때 배율을 약속한다: "앞으로 적는 Window 에 64 를 곱해서 읽어"
- SYN 두 개는 배율 합의 전이라 곱하지 않는다 → `Win=65535`
- 그 뒤는 헤더에 6380 이 적혀 있고, 와이어샤크가 × 64 = **408320** 으로 보여 준다
- 비유: 계산서에 "단위: 천 원" 을 적어 두는 것

## 체크 ② TIME_WAIT 는 어느 쪽에 남나 (11/2 실측)

- 예상: 먼저 끊은 쪽(nc·클라이언트)
- 방법: 클라이언트가 연결 → `hello` → 먼저 `close()`, 그 뒤 5초마다 `netstat -anp tcp` 로 그 포트를 찾음

```
클라이언트 포트 60546
  0.0초  127.0.0.1.60546  127.0.0.1.9000  TIME_WAIT
  ...    (5초마다 같은 줄)
 30.1초  127.0.0.1.60546  127.0.0.1.9000  TIME_WAIT
 35.1초  없음
```

- 결과: **클라이언트 쪽에만** 남았다. 서버 쪽(`9000 → 60546`) 줄은 처음부터 없었다
- 시간: 30.1초엔 있고 35.1초엔 없음 → 맥 `net.inet.tcp.msl = 15000`(15초) × 2 = 30초와 맞는다 (5초 간격이라 정확한 순간은 모름)
- 이유: 마지막 ACK 를 보낸 쪽이 그 ACK 가 사라졌을 때 다시 답하려고, 그리고 옛 패킷이 새 연결에 섞이지 않게 기다린다

## 체크 ③ keep-alive 켜고/끄고 (11/2 실측)

- 서버: `http_server.py` (`127.0.0.1:8765`, `protocol_version = "HTTP/1.1"`, 새 연결마다 로그)
- 켬: `curl -s -o /dev/null "http://127.0.0.1:8765/[1-100]"` → **새 연결 1개**
- 끔: 같은 명령 + `-H "Connection: close"` → **새 연결 100개**

| 어디로 | 요청 수 | 켬 | 끔 | 연결 수 (켬 / 끔) |
| --- | --- | --- | --- | --- |
| 내 맥 (루프백) | 100 | 0.019 ~ 0.027초 | 0.023 ~ 0.026초 | 1 / 100 |
| example.com (HTTPS, `--http1.1`) | 20 | 1.11 ~ 1.16초 | 2.97 ~ 3.02초 | 1 / 20 |

- 루프백에서는 차이가 거의 없다 → 핸드셰이크가 0.07ms(캡처 97→99번)라 100번 해도 수 ms
- 인터넷에서는 끔이 **약 2.6배** 느리다 → 연결마다 TCP 핸드셰이크 + TLS 핸드셰이크를 왕복 시간(RTT)만큼 다시 치른다
- 덤: 끔을 여러 번 돌린 뒤 8765 쪽 TIME_WAIT 가 615개 쌓였다 — 먼저 끊은 쪽(여기선 서버가 Connection: close 로 먼저 끊음? 확인 필요)
- 함정: HTTPS 는 curl 이 HTTP/2 로 붙는데, HTTP/2 는 `Connection` 헤더를 쓰지 않아 `Connection: close` 가 무시된다 → `--http1.1` 로 고정해야 비교가 된다
