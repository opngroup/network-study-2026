# 과제 B. 패킷 캡처와 keep-alive 측정 · 유진영

과제 A의 에코 서버를 와이어샤크로 들여다보고, 연결이 끝난 뒤 TIME_WAIT가 어느 쪽에 남는지 확인하고, keep-alive를 켜고 끌 때의 차이를 재 봅니다. 코드는 과제 A처럼 Node.js 표준 모듈만 씁니다.

## 한눈에 보는 결과

| 체크 | 확인한 것 | 결과 |
| --- | --- | --- |
| ① 패킷 캡처 | 연결 한 번에 오가는 패킷 | 연결 3개 → 데이터 4개 → 끊기 3개, 모두 10개 |
| ② TIME_WAIT 위치 | 먼저 끊은 쪽에 남는가 | 그렇다. 클라이언트가 먼저 끊으면 클라이언트에, 서버가 먼저 끊으면 서버에. 리눅스에서 약 60초 |
| ③ keep-alive | 켬 vs 끔, 요청 100번 | 루프백에서도 끔이 약 2배 느림. 끔은 연결 100개를 새로 만들고 TIME_WAIT가 **서버 쪽에** 쌓임 |

> 아래 결과는 테스트용 리눅스 환경에서 돌린 것입니다. macOS에서는 TIME_WAIT 시간(약 30초)과 끊기 패킷 수가 다를 수 있어서, 내 노트북에서 다시 돌려 비교해 보면 좋습니다.

## 파일 구성

| 파일 | 하는 일 |
| --- | --- |
| `client_once.js` | 체크 ①용. 에코 서버에 접속 → 1초 뒤 hello → 1초 뒤 끊기. 장면 사이를 1초씩 띄워 캡처에서 장면이 또렷이 나뉜다 |
| `time_wait_check.js` | 체크 ②. 서버와 클라이언트를 직접 띄우고, 한쪽이 먼저 끊은 뒤 운영체제의 TCP 연결 표를 주기적으로 읽는다 |
| `keepalive_bench.js` | 체크 ③. 요청 100번을 keep-alive 켬·끔으로 보내 시간과 연결 수를 잰다. `--url`로 인터넷 너머 서버도 잴 수 있다 |
| `lib/tcp_table.js` | 운영체제의 TCP 연결 표(netstat이 보여 주는 그 표)를 읽는 도우미. 리눅스·macOS·Windows 지원 |

설치할 것은 없습니다. Node.js 18.3 이상과, 체크 ①에 쓸 [와이어샤크](https://www.wireshark.org/)만 있으면 됩니다.

## 체크 ① 와이어샤크로 연결 한 번 들여다보기

### 내 노트북에서 하는 법

1. 와이어샤크를 켜고 인터페이스 목록에서 **Loopback: lo0**(macOS)를 더블클릭해 캡처를 시작한다
2. 위쪽 화면 필터 칸에 `tcp.port == 9000`을 넣고 Enter
3. 터미널 1: `node ../../../week-01/유진영/assignment-a/echo_server.js`
4. 터미널 2: `node client_once.js`
5. 3초쯤 뒤 와이어샤크 캡처를 멈춘다(빨간 네모)

### 결과: 패킷 10개, 세 장면

`capture/echo-once.pcap`을 와이어샤크로 열면 같은 화면을 볼 수 있습니다. 아래는 그 패킷 목록입니다. 49050은 운영체제가 클라이언트에 붙여 준 임시 포트입니다.

```
  #  시각(초)   방향            플래그        내용
  1  0.000000  49050 → 9000   [SYN]         Seq=0
  2  0.000027  9000 → 49050   [SYN, ACK]    Seq=0 Ack=1
  3  0.000036  49050 → 9000   [ACK]         Seq=1 Ack=1               ← ① 연결 끝 (0.04ms 만에)
  4  1.004737  49050 → 9000   [PSH, ACK]    Seq=1 Ack=1 Len=6  'hello\n'
  5  1.004746  9000 → 49050   [ACK]         Seq=1 Ack=7               ← "6바이트 받았어, 다음은 7번"
  6  1.005650  9000 → 49050   [PSH, ACK]    Seq=1 Ack=7 Len=6  'hello\n'  ← 에코
  7  1.005657  49050 → 9000   [ACK]         Seq=7 Ack=7               ← ② 데이터 끝
  8  2.008194  49050 → 9000   [FIN, ACK]    Seq=7 Ack=7               ← 클라이언트가 먼저 끊기
  9  2.009473  9000 → 49050   [FIN, ACK]    Seq=7 Ack=8               ← 서버: "알았어" + "나도 끊을게"
 10  2.009484  49050 → 9000   [ACK]         Seq=8 Ack=8               ← ③ 끊기 끝
```

| 장면 | 패킷 | 무슨 일 |
| --- | --- | --- |
| ① 연결 | 1~3 | 3-way handshake. "연결할래?" → "좋아, 너도 받을래?" → "응". 이 순간 서버 로그에 "연결됨"이 찍힌다 |
| ② 데이터 | 4~7 | hello 6바이트를 보내고(4), 받았다는 답장(5), 에코로 돌려받고(6), 받았다는 답장(7) |
| ③ 끊기 | 8~10 | 클라이언트 FIN → 서버 FIN+ACK → 클라이언트 ACK |

### 읽는 법

- **Seq와 Ack**: Seq는 "내가 보내는 데이터가 몇 번째 바이트부터인지", Ack는 "다음에 받고 싶은 번호"입니다. 4번에서 6바이트(1~6번)를 보내자 5번에서 `Ack=7`이 왔습니다. SYN과 FIN은 데이터가 없어도 번호를 하나 씁니다. 그래서 1번 SYN(Seq=0) 다음의 Ack가 1이고, 8번 FIN(Seq=7) 다음의 Ack가 8입니다.
- **0부터 세는 번호**: 실제 헤더의 순서 번호는 큰 무작위 수입니다. 와이어샤크와 위 목록은 보기 편하게 연결 시작을 0으로 놓고 다시 셉니다(상대 순번).
- **시각 열**: 1번과 4번 사이, 7번과 8번 사이가 정확히 1초씩 비어 있습니다. `client_once.js`가 쉬는 동안 연결은 열려 있지만 오가는 패킷은 하나도 없습니다. 연결은 "양쪽이 서로를 기억하는 약속"이라 할 말이 없으면 조용합니다.
- **Win 값**: 패킷 목록의 Win은 헤더에 적힌 원래 값입니다. SYN 때 배율(Window Scale)을 약속해 두고 그 뒤로는 작은 숫자에 배율을 곱해 읽습니다. 와이어샤크는 배율을 곱한 큰 숫자로 보여 줍니다.

## 체크 ② TIME_WAIT는 어느 쪽에 남나

### 실행

```bash
node time_wait_check.js                    # 클라이언트가 먼저 끊기 (nc에서 Ctrl+C와 같은 상황)
node time_wait_check.js --closer server    # 서버가 먼저 끊기 (HTTP Connection: close와 같은 상황)
```

스크립트가 서버와 클라이언트를 직접 띄우고 hello를 한 번 주고받은 뒤, 정한 쪽이 먼저 끊습니다. 그다음 운영체제의 TCP 연결 표를 5초마다 읽어 이 연결의 두 끝이 어떤 상태인지 보여 줍니다. 리눅스에서는 `/proc/net/tcp`를, macOS에서는 `netstat -anp tcp`를 읽습니다.

### 결과

| 경과 | 클라이언트가 먼저 끊음: 서버 끝 | 클라이언트 끝 | 서버가 먼저 끊음: 서버 끝 | 클라이언트 끝 |
| --- | --- | --- | --- | --- |
| 0초 | (없음) | **TIME_WAIT** | **TIME_WAIT** | (없음) |
| 30초 | (없음) | **TIME_WAIT** | **TIME_WAIT** | (없음) |
| 60.1초 | (없음) | **TIME_WAIT** | **TIME_WAIT** | (없음) |
| 65.1초 | (없음) | (없음) | (없음) | (없음) |

전체 출력은 `capture/timewait-client-closes.txt`, `capture/timewait-server-closes.txt`에 있습니다.

- **먼저 끊은 쪽에만 TIME_WAIT가 남습니다.** 나중에 끊은 쪽은 마지막 ACK를 받자마자 표에서 사라집니다.
- **리눅스는 60초**입니다. 60.1초엔 있고 65.1초엔 없습니다. 주영님이 맥에서 잰 값은 30초였습니다(MSL 15초 × 2).
- **왜 기다리나**: 마지막 ACK를 보낸 쪽은 그 ACK가 중간에 사라졌을 때 상대가 FIN을 다시 보내면 다시 답해 줘야 합니다. 또 같은 포트 쌍으로 새 연결을 바로 만들면, 늦게 도착한 옛 연결의 패킷이 새 연결에 섞일 수 있어서 잠시 그 포트 쌍을 비워 둡니다.

## 체크 ③ keep-alive 켬 vs 끔

### 실행

```bash
node keepalive_bench.js                                          # 이 컴퓨터 안의 테스트 서버(루프백)
node keepalive_bench.js --url https://example.com/ --count 20    # 인터넷 너머 서버
```

- **켬**: 연결 하나를 계속 다시 씁니다(HTTP/1.1의 기본 동작).
- **끔**: 요청마다 `Connection: close`를 붙입니다. 서버가 응답한 뒤 연결을 닫고, 다음 요청은 새 연결로 갑니다.

### 결과 (루프백, 요청 100번 × 3회)

```
회차  keep-alive  걸린 시간      요청당     새 TCP 연결
  1   켬            205.6 ms    2.056 ms      1개
  1   끔             99.1 ms    0.991 ms    100개
  2   켬             20.8 ms    0.208 ms      1개
  2   끔             42.8 ms    0.428 ms    100개
  3   켬             18.3 ms    0.183 ms      1개
  3   끔             40.2 ms    0.402 ms    100개

중앙값  켬 20.8 ms / 끔 42.8 ms  →  끔이 2.06배
테스트 서버가 받은 TCP 연결 총 303개
지금 TIME_WAIT: 서버 쪽 끝(8771→임시포트) 300개, 클라이언트 쪽 끝(임시포트→8771) 3개
```

- 1회차의 켬이 유독 느린 건 프로그램이 막 시작해서 코드가 아직 데워지지 않았기 때문입니다(Node의 JIT 컴파일). 그래서 3회 반복하고 중앙값으로 비교했습니다.
- **루프백에서도 끔이 약 2배 느렸습니다.** 왕복 시간이 거의 0인 루프백이라 핸드셰이크 자체보다는, 연결마다 소켓을 새로 만들고 정리하는 비용이 쌓인 결과입니다.
- **인터넷 너머 서버에서는 차이가 훨씬 커집니다.** 연결마다 TCP 핸드셰이크 왕복에 HTTPS라면 TLS 인사 왕복까지 다시 치르기 때문입니다. 주영님이 example.com에 curl로 잰 결과는 끔이 약 2.6배 느렸습니다. 이번 테스트 환경은 외부 접속이 막혀 있어서 `--url` 측정은 하지 못했습니다. 내 노트북에서 `node keepalive_bench.js --url https://example.com/ --count 20`으로 돌려 이 자리를 채우면 됩니다.

### 덤: TIME_WAIT는 서버 쪽에 300개

끔으로 300번 요청한 뒤 TIME_WAIT 300개가 **서버 쪽 끝**에 쌓였습니다. 클라이언트가 `Connection: close`를 보내면, 서버가 응답을 보낸 뒤 **먼저** 연결을 닫기 때문입니다. 체크 ②의 "먼저 끊은 쪽에 남는다"가 그대로 맞습니다. 주영님 노트의 "서버 쪽 TIME_WAIT 615개, 확인 필요"에 대한 답이기도 합니다. 클라이언트 쪽 3개는 켬 모드 3회가 끝날 때 클라이언트가 연결을 닫은 것입니다.

실무에서는 이렇게 이어집니다. 짧은 연결을 서버가 먼저 끊는 일이 대량으로 생기면 서버에 TIME_WAIT가 수만 개 쌓일 수 있습니다. keep-alive로 연결을 다시 쓰면 속도뿐 아니라 이 문제도 줄어듭니다.

## 예상과 달랐던 점

- **끊기가 4개가 아니라 3개였습니다.** 교과서의 연결 종료는 FIN → ACK → FIN → ACK 4번인데, 이번 캡처에서는 서버가 "알았어(ACK)"와 "나도 끊을게(FIN)"를 한 패킷(9번)에 담아 보냈습니다. Node는 상대의 FIN을 받으면 바로 자기 쪽도 닫는데, 운영체제가 ACK를 잠깐 미루는 사이(지연 ACK) FIN이 준비되어 둘이 함께 나갔습니다. 주영님의 맥 캡처처럼 4개로 나뉘어 보일 수도 있습니다. 둘 다 정상입니다.
- **루프백인데도 2배 차이가 났습니다.** 핸드셰이크 시간은 0.04ms라 무시할 만한데도, 연결을 100번 만들고 닫는 일 자체가 생각보다 비쌌습니다.

## 다음 과제와 이어지는 부분

- 과제 C에서 nginx를 앞에 둘 때도 같은 일이 생깁니다. nginx와 앱 서버 사이 연결을 keep-alive로 다시 쓰지 않으면 요청마다 연결을 새로 만들고 TIME_WAIT가 쌓입니다(nginx의 `upstream { keepalive ...; }` 설정).
- 5~6주차의 WebSocket·SSE는 연결 하나를 아주 길게 쓰는 방식이라, 이번에 본 "연결이 열려 있어도 조용하다"가 바로 하트비트가 필요한 이유가 됩니다.
