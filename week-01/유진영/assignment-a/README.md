# 과제 A. TCP 에코 서버 · 유진영

Node.js 표준 모듈 `net`만으로 만든 TCP 에코 서버와, 클라이언트 여러 개를 동시에 붙여 보는 테스트 클라이언트입니다. Express도 `http` 모듈도 쓰지 않고, 그 아래층인 TCP 소켓을 직접 다룹니다.

이 과제로 확인하려는 것은 두 가지입니다.

1. 서버는 접속한 상대를 **(IP, 포트)**로 구분하고, 클라이언트 쪽 포트는 운영체제가 임시로 고른다. (진단 퀴즈 Q07)
2. 서버가 **어느 주소에 바인딩하느냐**에 따라 어디서 접속할 수 있는지가 달라진다. (진단 퀴즈 Q04, 1주차 발표)

## 파일 구성

| 파일 | 하는 일 |
| --- | --- |
| `echo_server.js` | `--host`로 받은 주소에 바인딩하고, 접속한 클라이언트의 IP·포트를 로그로 남기며, 받은 바이트를 그대로 돌려준다 |
| `echo_client.js` | 클라이언트 여러 개를 동시에 붙여 각자의 출발지 포트와 답장을 출력한다 |
| `package.json` | 실행 명령을 `npm run`으로 쓸 수 있게 모아 둔 것. 설치할 의존성은 없다 |

코드 곳곳에 이유까지 주석으로 달아 두었습니다. 처음 읽을 때는 `echo_server.js`를 위에서부터 순서대로 읽으면 됩니다.

## 실행 방법

Node.js 18.3 이상이 필요합니다(`util.parseArgs` 사용). Node 22에서 확인했습니다. `npm install`은 하지 않아도 됩니다.

```bash
# 터미널 1: 서버
node echo_server.js                       # 127.0.0.1:9000 (이 컴퓨터 안에서만)
node echo_server.js --host 0.0.0.0        # 모든 IPv4 주소 (같은 와이파이의 다른 기기에서도)
node echo_server.js --port 9100           # 포트 바꾸기

# 터미널 2: 클라이언트
node echo_client.js                       # 3개 동시 접속
node echo_client.js --count 5
node echo_client.js --host 192.168.0.10   # 다른 기기에서 돌고 있는 서버로
nc 127.0.0.1 9000                         # 손으로 쳐 보기. 한 줄 입력하면 그대로 돌아온다
```

`npm run server`, `npm run server:all`, `npm run client`로도 실행할 수 있습니다.

## 배경 지식: 코드 뒤에서 일어나는 일

### 1. 서버 소켓의 일생

TCP 서버는 운영체제에 네 가지를 차례로 부탁합니다. Node는 이 단계를 몇 개의 함수로 묶어 두었습니다.

| 단계 | 운영체제에 하는 부탁 | Node 코드 | Python으로 쓰면 |
| --- | --- | --- | --- |
| 소켓 만들기 | 통신에 쓸 소켓 하나 주세요 | `net.createServer()` | `socket.socket()` |
| 바인딩 | 이 주소의 이 포트로 오는 연결을 제게 주세요 | `server.listen(port, host)` | `bind((host, port))` |
| 대기 | 이제부터 연결을 받습니다 (LISTEN 상태) | `server.listen(port, host)` | `listen()` |
| 연결 받기 | 연결 하나 꺼내 주세요 | `createServer`에 넘긴 콜백이 연결마다 불림 | `accept()` |

여기서 중요한 점이 두 가지 있습니다.

- **3-way handshake는 우리 코드가 하지 않는다.** SYN → SYN+ACK → ACK은 운영체제(커널)가 처리하고, 끝난 연결만 우리 콜백에 넘겨줍니다. 그래서 콜백이 불린 시점에는 이미 연결이 완성돼 있습니다.
- **소켓은 두 종류다.** 처음 만든 서버 소켓은 연결을 받기만 하고(LISTEN), 실제 대화는 연결마다 새로 생기는 소켓으로 합니다(ESTABLISHED). 콜백이 받는 `socket`이 바로 "이 손님 전용 통로"입니다.

### 2. 연결은 네 값으로 구분된다

TCP 연결 하나는 **(출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트)** 네 값의 조합으로 구분됩니다. 서버의 9000번 포트 하나에 클라이언트 세 개가 붙어도, 클라이언트 쪽 포트가 서로 달라서 세 연결이 섞이지 않습니다. 클라이언트 포트는 운영체제가 임시 포트 범위에서 비어 있는 번호를 골라 줍니다.

| 운영체제 | 임시 포트 범위 |
| --- | --- |
| 리눅스 | 32768 ~ 60999 |
| macOS | 49152 ~ 65535 |

코드에서는 `socket.remotePort`(서버가 본 상대 포트)와 `socket.localPort`(클라이언트가 본 내 포트)로 확인할 수 있습니다.

### 3. 바인딩 주소가 받을 손님을 정한다

컴퓨터는 IP 주소를 여러 개 가집니다. 루프백(127.0.0.1), 와이파이에서 받은 주소(192.168.x.x), Docker가 만든 가상 주소 등. 서버는 그중 어느 주소로 온 연결을 받을지 골라서 기다립니다.

| `--host` | 받는 연결 | 다른 기기에서 접속하면 |
| --- | --- | --- |
| `127.0.0.1` (기본값) | 이 컴퓨터 안에서 온 연결만 | `ECONNREFUSED` (연결 거부) |
| `0.0.0.0` | 이 컴퓨터의 모든 IPv4 주소로 온 연결 | 접속됨 |

**Node에서 특히 조심할 점**: `server.listen(9000)`처럼 host를 생략하면 Node는 IPv6를 쓸 수 있는 컴퓨터에서는 `::`(보통 IPv4까지 함께), 아니면 `0.0.0.0`에 바인딩합니다. 어느 쪽이든 모든 주소입니다. 즉 아무 설정 없이도 밖에서 접속됩니다. 편하지만 의도치 않게 외부에 열리기 쉬워서, 이 과제는 기본값을 `127.0.0.1`로 명시했습니다. 개발 서버를 0.0.0.0이나 `::`로 띄운 채 카페 와이파이에 붙으면 같은 와이파이의 다른 사람도 접속할 수 있습니다.

### 4. 스레드 없이 여러 손님을 받는 이유

Python 버전은 손님마다 스레드를 따로 만들어야 했습니다. `accept()`와 `recv()`가 데이터가 올 때까지 멈춰 서서 기다리기 때문입니다. Node는 **이벤트 루프** 하나가 모든 소켓을 지켜보다가, 데이터가 도착한 소켓의 콜백(`'data'`)만 불러 줍니다. 그래서 스레드 없이도 여러 손님을 동시에 받습니다. 대신 콜백 안에서 오래 걸리는 계산을 하면 그동안 다른 손님 전부가 기다리게 되니 주의해야 합니다.

### 5. TCP는 메시지가 아니라 바이트 흐름이다

`'data'` 이벤트 한 번이 상대가 보낸 메시지 하나와 같다는 보장은 없습니다. 한 번 보낸 것이 여러 번에 나뉘어 오거나, 두 번 보낸 것이 한 번에 올 수 있습니다. 작은 테스트에서는 우연히 한 번에 올 뿐입니다. 에코 서버는 받은 만큼 그대로 돌려주면 되니 문제가 없지만, 채팅처럼 메시지 단위가 필요한 프로그램은 줄바꿈이나 길이 값으로 경계를 직접 정해야 합니다. WebSocket이 "프레임"이라는 단위를 따로 두는 이유가 이것입니다. (5주차 주제)

### 6. 연결이 끝날 때

| 이벤트 | 언제 | 의미 |
| --- | --- | --- |
| `'end'` | 상대가 FIN을 보냈을 때 | "나는 더 보낼 게 없다". Node는 기본적으로 우리 쪽도 바로 닫는다 |
| `'close'` | 연결이 완전히 닫혔을 때 | 정상 종료든 에러든 마지막에 한 번 |
| `'error'` | 상대가 갑자기 사라졌을 때 등 | 이 리스너가 없으면 에러 하나에 서버 전체가 죽는다 |

먼저 연결을 끊은 쪽에는 **TIME_WAIT** 상태가 잠깐 남습니다. 서버를 끄고 바로 다시 켤 때 `Address already in use`가 날 수 있는 이유인데, Node는 리눅스·macOS에서 서버 소켓에 `SO_REUSEADDR`를 기본으로 켜 두어서 바로 다시 켤 수 있습니다. (2주차 주영님 발표 주제)

### 7. 백프레셔

`socket.write()`가 `false`를 돌려주면 "보낼 버퍼가 꽉 찼으니 잠깐 멈춰 달라"는 뜻입니다. 서버는 이때 받기를 잠시 멈추고(`pause`), 버퍼가 비면(`'drain'`) 다시 받습니다(`resume`). 상대가 못 따라오는데 계속 쓰면 데이터가 서버 메모리에 쌓이기 때문입니다. (2주차 발표 "흐름 제어"의 앱 버전)

## 무엇을 확인했나

> 아래 로그는 테스트 환경에서 돌린 결과입니다. 데모 전에 내 노트북에서 다시 돌려 이 자리를 내 결과로 바꿉니다.

### 1. 동시에 붙은 클라이언트 3개는 출발지 포트가 모두 다르다

```
$ node echo_client.js --count 3
client#1  출발지 127.0.0.1:41282  ->  127.0.0.1:9000  답장 "hello from client#1"
client#2  출발지 127.0.0.1:41288  ->  127.0.0.1:9000  답장 "hello from client#2"
client#3  출발지 127.0.0.1:41296  ->  127.0.0.1:9000  답장 "hello from client#3"
```

서버 쪽 로그:

```
[14:25:20] 서버 시작  127.0.0.1:9000 에서 기다리는 중 (Ctrl+C 로 종료)
[14:25:21] 연결됨    client=127.0.0.1:41282  ->  server=127.0.0.1:9000
[14:25:21] 연결됨    client=127.0.0.1:41288  ->  server=127.0.0.1:9000
[14:25:21] 받음      client=127.0.0.1:41282  20바이트  "hello from client#1"
[14:25:21] 연결됨    client=127.0.0.1:41296  ->  server=127.0.0.1:9000
[14:25:21] 받음      client=127.0.0.1:41288  20바이트  "hello from client#2"
[14:25:21] 받음      client=127.0.0.1:41296  20바이트  "hello from client#3"
[14:25:21] 상대가 끊음 client=127.0.0.1:41282
[14:25:21] 연결 닫힘  client=127.0.0.1:41282
```

서버 포트(9000)는 세 연결 모두 같고, 클라이언트 포트만 다릅니다. 서버는 이 차이로 세 연결을 구분합니다.

### 2. 127.0.0.1에 바인딩하면 다른 주소로는 접속이 거부된다

| 서버 바인딩 | 127.0.0.1로 접속 | 내 기기의 다른 IP로 접속 |
| --- | --- | --- |
| `127.0.0.1` | 성공 | `ECONNREFUSED` |
| `0.0.0.0` | 성공 | 성공 |

```
# 서버: node echo_server.js  (127.0.0.1)
$ node echo_client.js --host 192.0.2.2 --count 1
client#1 연결 실패: ECONNREFUSED

# 서버: node echo_server.js --host 0.0.0.0
$ node echo_client.js --host 192.0.2.2 --count 1
client#1  출발지 192.0.2.2:48394  ->  192.0.2.2:9000  답장 "hello from client#1"
```

휴대폰이나 다른 노트북으로 확인할 때는 macOS `ipconfig getifaddr en0`(리눅스 `hostname -I`)으로 내 IP를 찾아, 같은 와이파이의 다른 노트북에서 `nc <내 IP> 9000` 또는 `node echo_client.js --host <내 IP>`를 실행합니다.

### 3. 그 밖에 확인한 것

- 서버를 끄자마자 다시 켜도 `Address already in use`가 나지 않았다 (`SO_REUSEADDR`).
- 같은 포트로 서버를 두 번 켜면 두 번째는 "이미 다른 프로그램이 쓰고 있습니다"를 출력하고 끝난다 (`EADDRINUSE`).
- 서버가 없는 포트로 접속하면 클라이언트는 `ECONNREFUSED`로 끝난다.

## 예상과 달랐던 점

- 클라이언트 번호 순서와 서버가 데이터를 받은 순서가 섞였다. 연결 3개를 동시에 출발시키면 누가 먼저 끝날지는 정해져 있지 않다.
- 출발지 포트가 41282, 41288, 41296처럼 크고 가까운 숫자였다. 운영체제가 임시 포트 범위에서 고르기 때문이다.
- Node는 `listen(9000)`처럼 주소를 생략하면 밖에서도 접속되는 주소에 바인딩한다. Python 예제는 주소를 꼭 적어야 해서 몰랐던 부분이다.

## 데모 순서 (7분)

1. 터미널 1에서 `node echo_server.js` → "127.0.0.1:9000 에서 기다리는 중"
2. 터미널 2에서 `nc 127.0.0.1 9000` → hello를 치면 그대로 돌아온다. 서버 로그에 내 쪽 포트 번호가 찍힌 것을 보여 준다
3. `node echo_client.js --count 3` → 목적지는 같고 출발지 포트만 다른 것을 가리킨다 (Q07)
4. 주영님 노트북에서 `nc <내 IP> 9000` → 거부. 서버를 `--host 0.0.0.0`으로 다시 켜고 같은 명령 → 접속
5. "서버를 끄고 바로 다시 켜도 괜찮은 건 `SO_REUSEADDR` 덕분이고, 그게 필요한 이유가 TIME_WAIT" → 주영님 발표로 넘긴다

회사 와이파이가 기기끼리 통신을 막아 두었으면 4번이 안 될 수 있습니다. 미리 해 보고, 안 되면 휴대폰 핫스팟에 두 노트북을 붙입니다. 데모가 끝나면 0.0.0.0 서버는 꺼 둡니다.

## 과제 B와 이어지는 부분

- 이 서버에 접속하는 과정을 와이어샤크로 캡처하면 SYN → SYN+ACK → ACK와 FIN 교환을 볼 수 있다. 루프백으로 캡처할 때는 와이어샤크에서 `Loopback`(macOS `lo0`) 인터페이스를 고르고 필터를 `tcp.port == 9000`으로 둔다.
- `echo_client.js`는 클라이언트가 먼저 끊으므로, 끝난 직후 `netstat -an | grep 9000`을 보면 클라이언트 쪽 포트에 TIME_WAIT가 남아 있을 것이다.
