# 과제 A 학습 노트 — 10/24 까지 이해한 것

> 과제 A(TCP 에코 서버)를 단계별로 쌓으며 실행해 보고 정리한 것. 소켓 → 스레드 → 바인딩 → HTTP 순서.

## 1. 서버 소켓의 일생 — 콜센터 비유

```
socket()   전화기를 산다              아직 번호가 없다
bind()     번호를 단다                "127.0.0.1 의 9000번"  ← IP + 포트
listen()   영업 시작                  OS 가 연결 대기열을 만든다
accept()   대기열에서 연결 하나를 꺼낸다  ★ 손님 전용 소켓(상담 회선)이 새로 생긴다
recv/send  그 회선으로 대화한다
```

- 소켓은 **두 종류**다. 대표번호 소켓(`server`, LISTEN)은 연결을 받기만 하고, 대화는 `accept()` 가 돌려준 새 소켓(`conn`, ESTABLISHED)으로 한다
- `accept()` 는 `(새 소켓, (상대 IP, 상대 포트))` 를 돌려준다. 클라이언트 IP·포트 로그는 여기서 나온다
- `recv()` 가 `b""` 를 돌려주면 상대가 연결을 닫은 것이다

## 2. 3-way handshake 는 내 코드가 아니라 OS 가 한다

- `listen()` 만 하고 `accept()` 를 안 불러도 `nc` 접속이 **성공**했다. `netstat` 에 서버 쪽 끝이 `ESTABLISHED` 로 있었고, `lsof` 의 Python 줄은 LISTEN 하나뿐이었다
- 즉 SYN → SYN+ACK → ACK 은 커널이 처리하고, 끝난 연결을 **대기열**에 넣어 둔다
- 대기열에 담기는 건 "요청"이 아니라 **연결**이다. 손님이 보낸 글자는 그 연결의 **수신 버퍼**에 따로 쌓인다
  - `accept` 전에 3명이 "나는 철수" 등을 보냈더니 `netstat` Recv-Q 에 각 13바이트가 쌓여 있었고, `accept` → `recv` 하자 그대로 나왔다
- `accept()` 는 "누구와"(연결·주소)를, `recv()` 는 "무슨 말"(데이터)을 준다

## 3. TCP 상태

- 연결마다 커널이 상태를 들고 있다. 맥 SDK `netinet/tcp_fsm.h` 에 `TCPS_CLOSED`(0) ~ `TCPS_TIME_WAIT`(10) 11개가 상수로 있다
- 오늘 본 상태: `LISTEN`, `ESTABLISHED`, `TIME_WAIT`
- **먼저 끊는 쪽에 TIME_WAIT 가 남는다** — 둘 다 실제로 봤다
  - `nc` 가 먼저 끊음 → 손님 쪽 포트(59125 등)에 TIME_WAIT
  - 서버를 kill 해서 서버가 먼저 끊음 → 서버 쪽 9001 에 TIME_WAIT → 다시 켜자 `Address already in use`

## 4. 여러 손님 받기 — 반복 두 겹, 그리고 스레드

| 단계 | 구조 | 결과 |
| --- | --- | --- |
| accept 한 번 | 손님 하나와 대화하고 끝 | 손님이 끊으면 프로그램 종료 |
| 바깥 `while` | 손님 반복 + 대화 반복 | 다음 손님은 받지만, A 가 붙어 있으면 B 는 2.5초 기다림 |
| 손님마다 스레드 | 안내 데스크(Main)는 `accept` 만, 대화는 상담원(스레드) | 3명이 동시에 바로 메아리 |

- 손님 하나의 `recv()` 에서 멈춰 있으면 그동안 `accept()` 를 못 한다 → 상담원을 늘린 것이 스레드
- 동시 3명일 때 `lsof`: 서버 포트는 셋 다 9000, **클라이언트 포트는 각각 다름**(OS 가 골라 붙인 출발지 포트). 연결은 (출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트) 4개 값으로 구분된다

## 5. 스레드

- **프로세스** = 콜센터 건물, **스레드** = 그 안에서 코드를 한 줄씩 실행하는 상담원. 프로그램에는 최소 하나(MainThread)가 있다
- 스레드마다 **따로**: 실행 위치, 지역 변수(`conn`, `data`) / **공용**: 전역 변수, 열린 소켓, 화면 출력
- `recv()` 에서 기다리는 스레드는 잠들어 CPU 를 쓰지 않는다. 데이터가 오면 OS 스케줄러가 그 스레드만 깨운다 → 기다림이 대부분인 네트워크 서버에 잘 맞는다
- 손님 0명 → 스레드 1개, 3명 → 4개 (`ps -M` 으로 확인)

## 6. 경쟁 조건과 뮤텍스 (과제 밖 덤)

스레드 3개가 공용 `count` 에 +1 을 반복하는 실험.

| 실험 | 모양 | 결과 |
| --- | --- | --- |
| race1 | `count = count + 1` | 우연히 정확 (GIL 때문에 틈이 좁아서 — 코드는 틀렸다) |
| race2 | 읽기 → `sleep(0)` → 쓰기 | 3,000 중 약 1,000 만 남음 |
| race3 | ①~③ 전부 `with lock:` | 정확, 대신 약 1.5배 느림 |
| race4a | ① 잠금 / ② / ③ 잠금 (쪼갬) | 다시 약 1,000 — 락을 걸었는데도 틀림 |
| race4b | ② 밖, ①③ 을 한 번에 잠금 | 정확하고 race3 보다 빠름 |

- **경쟁 조건**: 공용 값을 "읽기 → (틈) → 쓰기" 하는 사이 다른 스레드가 끼어들어 갱신이 사라지는 것 (잃어버린 갱신)
- **뮤텍스(락)**: 임계 구역을 한 번에 한 스레드만 실행하게 하는 자물쇠
- 원칙: **읽기-쓰기는 끊기지 않는 한 덩어리로(원자성)** 잠그고, 오래 걸리는 일은 밖으로
- 멀티스레드 로그의 줄 순서를 실제 실행 순서로 믿으면 안 된다 (`print` 도 공용 자원)

## 7. 바인딩과 다른 기기 접속

- `127.0.0.1` = 루프백(lo0), 같은 기기 안에서만. `0.0.0.0` = 모든 인터페이스(lo0 + Wi-Fi en0)
- 127.0.0.1 바인딩 → 휴대폰 접속 안 됨
- 0.0.0.0 바인딩인데 **회사 Wi-Fi 에서는 휴대폰이 못 들어왔다**
  - 서버는 `*:9000 LISTEN`, 방화벽 꺼짐, 맥에서 자기 Wi-Fi IP 로는 접속됨
  - 맥에서 휴대폰을 `arp` 로 찾으니 `incomplete` → 공유기가 기기끼리 통신을 막는 것으로 보임(클라이언트 격리, 추정)
- 휴대폰 **핫스팟**으로 우회했더니 핫스팟이 **IPv6 전용**이었다 (맥 IPv4 는 변환용 `192.0.0.2` 뿐)
  - `AF_INET6` + `bind(("::", 9000))` 로 바꾸자 휴대폰에서 `http://[맥 IPv6]:9000` 접속 성공
  - IPv6 는 앞 네 칸(`2001:2d8:219b:f5e3`)이 같으면 같은 네트워크

## 8. 끊는 방식 두 가지와 HTTP

- **FIN**: 정중하게 끊기 → `recv()` 가 `b""`
- **RST**: 연결을 버리기 → `recv()` 가 `ConnectionResetError`
- 휴대폰 브라우저로 에코 서버에 접속 → `ERR_INVALID_RESPONSE`
  - 연결·전송은 성공했는데, 에코가 브라우저의 요청을 그대로 돌려줘서 HTTP 응답 형식이 아니었다. 브라우저는 RST 로 끊었다
- HTTP 응답은 정해진 모양의 텍스트다: `HTTP/1.1 200 OK\r\n` + 헤더 + **빈 줄** + 본문
  - `Content-Length` 는 글자 수가 아니라 **바이트 수** (한글 1자 = 3바이트). 휴대폰 화면 본문이 정확히 101바이트였다
- 그렇게 보내자 휴대폰에 "안녕! 에코 서버입니다"와 휴대폰 자신의 IPv6·포트가 떴다 — 프레임워크 없이 소켓만으로 만든 웹 서버
