UNIT 1

캐시는 어디에 있고, 언제까지 믿나

요청은 가까운 곳에 저장된 응답이 있으면 거기서 멈춘다. 그 응답은 max-age 동안만 확인 없이 쓴다.

어디에: 저장소는 두 종류다

브라우저 캐시private · 나만 쓴다
→
CDNshared · 모두 같이
→
nginx·프록시설정하면 shared
→
앱 서버원본(origin)

private은 내 냉장고이고, shared는 동네 마트 진열대입니다. 진열대에 놓인 것은 다음 사람도 가져갑니다.

함정

개인 정보가 담긴 응답이 shared 캐시에 들어가면 남에게 내 화면이 갑니다. 막는 방법은 Cache-Control: private입니다.

언제까지: fresh와 stale

  • fresh(신선): max-age 안. 서버에 묻지도 않고 바로 씁니다.
  • stale(상함): 기한이 지남. 버리지 않고 "아직 맞아요?" 하고 재검증합니다.
출제 예상 · 계산
Q응답에 max-age=3600, age: 1254. 내 브라우저에서 남은 신선 시간은? A3600 − 1254 = 2346초(약 39분). age는 CDN이 이미 들고 있던 시간입니다. CDN에서 온 응답은 갓 만든 게 아닐 수 있습니다.

캐시의 판단은 딱 세 갈래

신선하다그냥 쓴다200 (disk cache)

요청이 아예 안 나감. 서버 로그에도 없음

상했고, 검증 값이 있다물어본다304 · 본문 0B

헤더만 오감

상했고, 검증 값이 없다다시 받는다200 · 본문 전체

처음 받는 것과 같음

검증 값은 두 가지입니다. ETag(내용의 지문)와 Last-Modified(마지막 수정 시각).

쪽집게

DevTools Size 열의 (disk cache)는 "서버에 안 갔다"는 뜻입니다. "배포했는데 화면이 안 바뀌어요"의 단골 원인이고, 서버 로그를 아무리 봐도 안 나옵니다.

함정 · 휴리스틱 캐시

Cache-Control이 없으면 캐시를 안 하는 게 아닙니다. Last-Modified만 있으면 브라우저가 기한을 추측해서 캐시합니다. 그래서 API 응답에는 Cache-Control을 꼭 적습니다.

출제 예상
QF5와 Ctrl+Shift+R은 뭐가 달라요? AF5는 신선한 것도 재검증합니다(max-age=0을 붙여 보냄). 강력 새로고침은 캐시를 무시하고 처음부터 받습니다(no-cache를 붙여 보냄).

UNIT 2 · Q20

Cache-Control: no-cache는 저장 금지가 아니다

no-cache는 저장하되 매번 확인, no-store는 저장 금지.

no-cache저장 OK, 쓰기 전에 매번 확인

신선 기간 0과 같습니다. 매번 묻지만 안 바뀌었으면 304로 본문을 아낍니다.

예: SPA의 index.html

no-store아예 저장하지 마

디스크에도 안 남깁니다. 매번 본문 전체를 받습니다.

예: 계좌 내역, 개인정보 화면, 1회용 토큰

외우는 법

no-cache는 "캐시 쓰지 마"가 아니라 "확인 없이 쓰지 마"입니다. 저장을 막는 건 이름에 store가 들어간 쪽입니다.

함정 두 개

① "캐시 끄기"라고 no-cache를 넣었는데 개인정보가 디스크에 남는 경우. ② "확실히 하려고" 모든 응답에 no-store를 넣어 304의 이득을 다 버리는 경우. 항상 최신이면 되는 곳은 no-cache가 더 쌉니다.

자주 쓰는 여덟 개는 다섯 묶음으로 외운다

묶음값뜻
기한max-age=NN초 동안 신선. 묻지 않고 쓴다
s-maxage=NCDN 같은 shared 캐시에만 주는 기한. max-age=60, s-maxage=3600이면 브라우저 1분, CDN 1시간
누가publicshared 캐시도 저장해도 된다
private브라우저만 저장
확인 방식no-cache저장은 하되 매번 재검증
must-revalidate상한 뒤엔 반드시 확인. 원본이 죽어도 상한 걸 몰래 주지 말고 504
저장 금지no-store저장 금지
최적화immutable기간 안엔 새로고침해도 묻지 마. 파일명에 해시가 붙은 번들에만
stale-while-revalidate=N상한 뒤 N초까지는 옛것을 즉시 주고 뒤에서 새로 받아 둔다. React SWR 이름의 유래
출제 예상
Q네이버는 왜 no-cache, no-store, must-revalidate를 다 넣었어요? A지시어 일부를 모르는 옛 브라우저·프록시 대비입니다. 실제로 이기는 건 no-store. 참고로 Pragma: no-cache는 HTTP/1.0 헤더라 지금은 안 써도 됩니다.

UNIT 3 · Q21

ETag → If-None-Match → 304

서버가 지문(ETag)을 주고, 브라우저가 그 지문을 들고 다시 물으면, 안 바뀌었을 때 304와 빈 본문이 온다.

브라우저서버
① 첫 요청GET /orders/7
200 · ETag: "v3" · 본문지문과 함께 저장
… max-age가 지나 상함 …
② 지문 들고GET /orders/7 · If-None-Match: "v3"
304 Not Modified · 본문 없음③ 그대로면

바뀌었으면 ③에서 200과 새 ETag, 새 본문이 옵니다. If-None-Match는 "내가 가진 건 이 지문이니, 이것과 다르면 보내 줘"라는 뜻입니다.

쪽집게 · 실측

MDN 첫 화면: 처음엔 200, 본문 118,790B. 같은 지문을 들고 다시 물으니 304, 본문 0B(11/17). 발표 때는 bash demo.sh etag로 그대로 보여 줍니다.

함정 · 304는 공짜가 아니다

아끼는 건 본문 전송뿐입니다. 요청과 왕복은 그대로 들고, 서버도 지문을 계산하려고 DB를 읽을 수 있습니다. 그래서 "아예 안 묻는" max-age와 같이 씁니다.

더 물어볼 만한 것

주제알아 둘 것
ETag 만드는 법본문 해시, DB의 updated_at, 버전 번호. 싼 값으로 만들면 DB 한 칸만 읽고 304를 줄 수 있다
강한 vs 약한"abc"는 바이트까지 같음, W/"abc"는 의미만 같음. 304 판단엔 둘 다 됨. jQuery는 gzip으로 받으면 W/가 붙는다(압축으로 바이트가 달라져서)
Last-ModifiedIf-Modified-Since로 묻는 옛 방식. 1초 단위라 1초 안에 두 번 바뀌면 못 잡는다. 둘 다 있으면 ETag 우선
If-MatchPUT 때 "내가 본 게 v3일 때만 바꿔 줘". 어긋나면 412 Precondition Failed. 동시 수정을 막는 낙관적 잠금
304에 Cache-Control이 오면저장된 응답의 헤더를 갱신하고 신선 기간을 새로 시작한다
외우는 법

None-Match는 "안 맞으면 줘"(조회용, 304), Match는 "맞을 때만 해"(수정용, 412). 우유팩 제조 번호를 들고 마트에 전화하는 게 If-None-Match입니다.

UNIT 4 · Q23

같은 주소, 다른 응답: 콘텐츠 협상과 Vary

브라우저가 Accept-*로 원하는 걸 말하고, 서버가 골라서 Content-*로 알린다. 이게 콘텐츠 협상이다.

브라우저가 보냄서버가 알림예
AcceptContent-Type같은 /orders/7을 API엔 JSON, 주소창엔 HTML로. 이미지 CDN이 AVIF·WebP 고르기
Accept-LanguageContent-Language한국어 페이지냐 영어 페이지냐
Accept-EncodingContent-Encodinggzip·br 압축. MDN은 119KB → 16.5KB

ko-KR,ko;q=0.9,en;q=0.8의 q는 선호도(0~1)입니다. "한국어 제일, 영어는 차선".

  • MDN은 Accept-Language: ko에 302 → /ko/로 답합니다. 같은 주소에서 바로 주지 않고 언어별 주소로 보내면 캐시·검색·공유 링크가 단순해집니다.
  • GitHub는 ko를 보내도 content-language: en-US. 협상은 요청일 뿐이고, 없으면 기본값을 줍니다.

Vary: "주소만 보지 말고 이 헤더도 보고 구분해"

캐시의 기본 열쇠는 메서드 + URL입니다. 협상을 하면 같은 주소에 응답이 여러 개가 되니, Vary: Accept-Language로 열쇠에 언어 값을 더하게 합니다.

함정 · Vary를 빼먹으면

한국인이 먼저 받은 한국어 페이지가 CDN에 저장되고, 다음 미국인도 한국어를 받습니다. gzip을 못 읽는 클라이언트가 압축 본문을 받기도 합니다. 그래서 거의 모든 사이트에 Vary: Accept-Encoding이 있습니다(nginx gzip_vary on;).

함정 · 반대로 너무 많이 붙이면

Vary: Cookie, Vary: User-Agent처럼 값이 제각각인 헤더를 걸면 캐시가 잘게 쪼개져 거의 안 맞습니다. GitHub처럼 열 개 넘게 붙인 응답은 사실상 shared 캐시에 넣을 생각이 없는 것이고, 실제로 private입니다.

쪽집게

로그인 사용자별 응답은 Vary가 아니라 private로 막는다. 같은 주소에 다른 걸 주면 Vary, 내 것이면 private.

실무에서는: 사이트마다 정책이 다르고, 다 이유가 있다

내용이 바뀌면 주소가 바뀌는 파일은 길게, 주소는 그대로인데 내용이 바뀌는 HTML·API는 짧게 + ETag.

네이버 첫 화면no-cache, no-store, must-revalidate로그인·개인화. 아예 안 남김
GitHub 첫 화면max-age=0, private, must-revalidate + ETag W/나만 저장, 매번 확인, 304로 아낌

  • "배포했는데 화면이 안 바뀐다" = index.html에 긴 캐시가 걸렸거나 CDN이 HTML을 들고 있는 경우.

UNIT 6 · 지난주

과제 C와 이어지는 곳

같은 멱등 키로 두 번 보내도 주문은 1건이었고, 500은 앱이, 502·504는 nginx가 만들었다.

502거절당했다

OS는 살아 있고 포트를 듣는 프로세스가 없으면 OS가 즉시 RST로 거절. 응답 도중 끊겨도 502.

504대답이 없다

앱 컨테이너를 통째로 끄면 IP가 사라져 SYN에 답할 OS조차 없음 → 2초 기다리다 504.

외우는 법

거절은 502, 침묵은 504. 더 정확히는 nginx error.log의 while connecting(연결 자체가 안 됨)과 while reading response header(답이 늦음)를 봅니다.

  • nginx는 keepalive로 재사용하던 연결이 끊기면 GET은 몰래 한 번 더 보내고, POST는 안 보냅니다.
  • 504가 나도 앱은 일을 계속합니다. 아무도 받지 않을 응답을 끝까지 만듭니다.
  • 멱등 키는 클라이언트가 버튼을 누른 한 번마다 UUID로 만들고, 재시도에는 같은 키를 씁니다. 서버가 2대면 메모리 저장소는 깨지니 Redis로 옮깁니다.
오늘 주제로 넘어가는 다리

멱등 키 저장소도, 캐시도 "같은 요청엔 저장된 응답"입니다. 차이는 누가 저장하느냐(서버 vs 브라우저·CDN)와 언제까지 믿느냐(키 24시간 vs max-age).

시험 직전 5문장

이 다섯 줄만은 입으로 말할 수 있게

  1. 캐시는 신선하면 묻지 않고, 상하면 지문을 들고 묻는다.
  2. no-cache는 매번 확인, no-store는 저장 금지. (Q20)
  3. If-None-Match로 물었는데 그대로면 304, 본문 없음. 304는 본문만 아낀다. (Q21)
  4. 같은 주소에서 Accept-*로 고르는 건 콘텐츠 협상. 그러면 Vary를 붙이고, 내 것이면 private. (Q23)
  5. 파일명에 해시가 있으면 1년, HTML은 no-cache.
