UNIT 1 · 바탕

준비: 웹은 요청과 응답을 주고받는다

브라우저가 요청을 보내고 서버가 응답을 돌려준다. 둘 다 앞에 "헤더"라는 메모를 붙이고, 헤더는 요청에도 응답에도 있다.

요청과 응답

웹페이지를 연다는 건 브라우저가 서버에 "이 주소의 것을 주세요"라고 묻고(요청, request), 서버가 "여기 있어요"라고 답하는(응답, response) 일입니다. 페이지 하나를 열 때도 HTML, 그림, CSS, JS마다 요청과 응답이 한 쌍씩 오갑니다.

브라우저요청을 보낸다 (클라이언트)
⇄
서버응답을 돌려준다

헤더와 본문: 택배 상자에 붙인 송장

요청과 응답은 둘 다 두 부분으로 되어 있습니다. 앞쪽 헤더(header)는 "이름: 값" 꼴의 짧은 메모 여러 줄이고, 뒤쪽 본문(body)은 실제 내용물(HTML, 그림 파일)입니다. 택배로 치면 헤더는 상자에 붙인 송장, 본문은 상자 안의 물건입니다.

GET /logo.png HTTP/1.1        ← 요청: "logo.png 주세요"
Host: example.com             ← 요청 헤더들
Accept-Language: ko

HTTP/1.1 200 OK               ← 응답: "200, 잘 찾았어요"
Content-Type: image/png       ← 응답 헤더들
Cache-Control: max-age=3600
ETag: "v3"
                              ← 빈 줄 다음부터 본문
(그림 파일 내용)

응답 첫 줄의 상태 코드는 결과 요약입니다. 200은 "여기 있어요", 404는 "그런 거 없어요", 오늘 나올 304는 "네가 가진 거 그대로 써"입니다.

오늘 나오는 헤더는 누가 보내나

오늘 공부의 절반은 이 표입니다. 헤더마다 요청에 싣는 것(브라우저가 보냄)과 응답에 싣는 것(서버나 캐시가 보냄)이 정해져 있습니다. 헷갈리면 여기로 돌아오세요.

헤더어디에 싣나한 줄 뜻
Cache-Control요청과 응답 둘 다응답에서는 "이 응답을 이렇게 보관해"(서버의 보관 규칙), 요청에서는 "이번엔 이렇게 해 줘"(브라우저의 부탁). 단원 4·5
ETag응답이 내용의 지문. 내용이 바뀌면 값도 바뀐다. 단원 3
If-None-Match요청"내가 가진 지문은 이건데, 이것과 다르면 보내 줘." 단원 3
Last-Modified응답이 내용을 마지막으로 고친 시각
If-Modified-Since요청"이 시각 뒤로 바뀌었으면 보내 줘"
Age응답 (중간 캐시가 붙임)"내가 이 응답을 들고 있은 지 몇 초째야." 단원 2
Accept, Accept-Language, Accept-Encoding요청"이런 형식·언어·압축으로 주면 좋겠어." 단원 6
Content-Type, Content-Language, Content-Encoding응답"실제로 이 형식·언어·압축으로 줬어." 단원 6
Vary응답"캐시야, 주소만 보지 말고 이 요청 헤더도 보고 구분해." 단원 6
외우는 법 · 이름만 보고 방향 알기

If-로 시작하면 요청입니다(조건을 거는 쪽은 받는 사람). Accept-도 요청(원하는 걸 말하는 쪽). Content-는 응답(실제로 보낸 본문 설명). Cache-Control만 양쪽에 다 나옵니다.

함정

"Cache-Control은 서버가 보내는 헤더"라고만 알면 단원 5에서 막힙니다. 응답의 Cache-Control은 서버가 정한 보관 규칙이고, 요청의 Cache-Control은 브라우저가 이번 한 번만 하는 부탁입니다. 같은 이름, 다른 역할입니다.

쪽집게 · 눈으로 보는 법

DevTools(F12) → Network 탭 → 요청 하나 클릭 → Headers에 Request Headers(내가 보낸 것)와 Response Headers(받은 것)가 따로 나옵니다. 터미널에서는 curl -v 주소의 > 줄이 요청, < 줄이 응답입니다.

UNIT 2

캐시가 뭔가: 한 번 받은 걸 또 받지 않기

캐시는 한 번 받은 응답을 가까운 곳에 복사해 두고, 다음에 같은 요청이 오면 그 복사본을 쓰는 것이다.

왜 필요한가

네이버 첫 화면을 열 때마다 로고 그림을 서버에서 새로 받는다고 생각해 보세요. 로고는 몇 달씩 안 바뀌는데 매번 받으면 셋 다 손해입니다.

  • 느리다: 서버는 멀리 있습니다. 내 컴퓨터에 있는 복사본은 0초입니다.
  • 서버가 힘들다: 같은 걸 수백만 명에게 계속 보내야 합니다.
  • 데이터가 든다: 휴대폰 요금, 서버 전송 비용.

그래서 받은 응답을 저장해 두고 다시 씁니다. 이 저장소, 또는 저장해 두는 일을 캐시(cache)라고 합니다.

외우는 법 · 냉장고

우유를 마실 때마다 공장에 가지 않고 냉장고에 넣어 두는 것과 같습니다. 냉장고가 캐시, 공장이 서버(원본, origin)입니다.

대신 생기는 문제: 복사본이 낡는다

서버의 내용이 바뀌었는데 내 복사본은 옛것이면, 사용자는 틀린 화면을 봅니다. 그래서 캐시에는 두 가지 규칙이 꼭 필요합니다.

  1. 얼마 동안 그냥 믿고 쓸까? → 유통기한(max-age). 이 단원 아래.
  2. 기한이 지나면 어떻게 확인할까? → 지문(ETag)을 들고 묻기. 단원 3.
쪽집게

캐시 이야기는 전부 "빨라지고 싶다"와 "낡은 걸 보여 주면 안 된다" 사이의 줄다리기입니다. 오늘 나오는 헤더는 모두 이 둘의 균형을 맞추는 도구입니다.

캐시는 어디에 있나

브라우저 캐시내 컴퓨터 안 · 나만 씀
→
CDN세계 곳곳의 복사 서버 · 모두 같이
→
프록시 (nginx 등)서버 앞 문지기 · 설정하면
→
원본 서버진짜 내용을 만드는 곳

요청은 왼쪽에서 오른쪽으로 갑니다. 가는 길에 쓸 만한 복사본이 있으면 거기서 멈추고 그 복사본이 응답으로 돌아옵니다.

  • CDN(Content Delivery Network): 원본 서버 대신 세계 곳곳에 둔 "대리점" 서버입니다. 서울 사용자는 미국 원본 대신 서울 대리점에서 받습니다. Cloudflare, CloudFront가 그 예입니다.
  • private 캐시(개인용): 브라우저 캐시. 내 장바구니처럼 나에게만 맞는 응답도 둬도 됩니다.
  • shared 캐시(공용): CDN, 프록시. 한 사람이 받은 응답을 다른 사람에게도 줍니다.
함정

"내 정보" 화면이 shared 캐시에 들어가면 다음 사람이 내 화면을 받습니다. 서버가 응답에 Cache-Control: private를 붙여 "공용 캐시는 저장하지 마"라고 막습니다.

얼마나 믿나: 유통기한 max-age

서버는 응답에 Cache-Control: max-age=3600처럼 기한을 적어 보냅니다. "받은 뒤 3600초(1시간) 동안은 나한테 묻지 말고 그냥 써"라는 뜻입니다.

fresh (신선)기한 안: 그냥 쓴다

서버에 요청을 보내지도 않습니다. DevTools Size 열에 (disk cache)나 (memory cache)로 보입니다.

stale (상함)기한 지남: 확인한다

바로 버리지 않습니다. 내용은 아직 맞을 수도 있으니, 서버에 "이거 아직 맞아요?" 하고 묻습니다(재검증). 단원 3.

출제 예상 · 계산
QCDN에서 받은 응답에 max-age=3600과 Age: 1254가 있다. 내 브라우저에서 남은 신선 시간은? A3600 − 1254 = 2346초, 약 39분. Age는 CDN이 이 응답을 이미 들고 있던 시간입니다. 기한은 원본 서버가 만든 순간부터 세기 때문에, CDN에서 받은 응답은 그만큼 덜 남아 있습니다.
함정 · Cache-Control이 없으면?

"규칙이 없으니 저장 안 하겠지"가 아닙니다. Last-Modified만 있으면 브라우저가 기한을 스스로 추측합니다(휴리스틱 캐시). 이때 브라우저가 짐작하는 건 "지금 최신인가"가 아니라(방금 받았으니 최신입니다) "앞으로 얼마 동안 안 바뀔까"입니다.

1년 동안 안 고친 파일은 앞으로도 한동안 안 바뀔 테니 길게, 1시간 전에 고친 파일은 곧 또 바뀔 수 있으니 짧게 씁니다. 보통 마지막으로 고친 뒤 지난 시간의 10%를 기한으로 잡습니다. 1년 전에 고친 파일이면 약 36일, 1시간 전이면 6분입니다.

개발자가 정하지 않은 기한이 생기는 셈이라, API 응답에는 Cache-Control을 꼭 적습니다.

쪽집게

(disk cache)로 받은 요청은 서버에 가지도 않았으니 서버 로그에도 없습니다. "배포했는데 사용자 화면이 안 바뀌어요"의 단골 원인입니다.

UNIT 3 · Q21

아직 맞는지 묻기: ETag → If-None-Match → 304

서버가 내용의 지문(ETag)을 주고, 기한이 지나면 브라우저가 그 지문을 들고 묻는다. 안 바뀌었으면 서버는 본문 없이 304만 보낸다.

지문이 왜 필요한가

기한이 지난 복사본이 아직 맞는지 확인하려면, 내용 전체를 다시 받아 비교하는 건 의미가 없습니다(그럼 그냥 다시 받는 것과 같으니까요). 그래서 서버는 응답마다 내용을 대표하는 짧은 값을 붙여 줍니다. 이게 ETag(Entity Tag)입니다. 우유팩에 찍힌 제조 번호처럼, 내용이 바뀌면 값도 바뀝니다.

흐름

브라우저서버
① 처음GET /orders/7
200 OK · ETag: "v3" · max-age=60 · 본문셋 다 저장
… 60초 동안은 묻지 않고 복사본을 씀. 60초가 지나 상함 …
② 지문 들고GET /orders/7 · If-None-Match: "v3"
304 Not Modified · 본문 없음③ 그대로면
  1. 서버가 응답에 ETag: "v3"를 붙여 보내고, 브라우저가 본문과 함께 저장합니다.
  2. 기한이 지나면 브라우저가 요청에 If-None-Match: "v3"를 붙입니다. "내 지문은 v3인데, 이것과 다르면(None-Match) 새 걸 보내 줘."
  3. 서버가 지금 지문을 계산해 비교합니다. 같으면 304, 본문 없음. 브라우저는 저장해 둔 본문을 씁니다. 다르면 200과 새 ETag, 새 본문.
출제 예상 · Q21
Q브라우저가 If-None-Match: "abc123"을 붙여 요청했고 리소스는 그대로다. 서버의 응답은? A304 Not Modified, 본문 없음.
함정 · 304는 에러가 아니다

4xx·5xx처럼 무언가 잘못된 게 아닙니다. 3xx는 "다른 곳을 봐"라는 묶음이고, 304는 "네가 이미 가진 걸 봐"입니다. 사용자 화면은 정상으로 나옵니다.

실제로 해 보면

① 처음 받기
HTTP/2 200   etag: "3a8ce56f…"   cache-control: public, max-age=3600   본문 118,790B
② 같은 지문을 If-None-Match에 넣어 다시 묻기
HTTP/2 304   etag: "3a8ce56f…"   본문 0B

MDN 첫 화면을 curl로 받은 실제 값입니다(11/17). 저장소의 bash demo.sh etag로 똑같이 볼 수 있습니다.

함정 · 304도 공짜는 아니다

아끼는 건 본문 전송뿐입니다. 요청을 보내고 답을 기다리는 왕복 시간은 그대로 들고, 서버도 지문을 계산해야 합니다. 그래서 "아예 안 묻는" max-age와 같이 씁니다.

한 걸음 더

주제알아 둘 것
ETag는 무엇으로 만드나본문의 해시, DB의 updated_at, 버전 번호. 해시는 본문을 다 만들어야 나오니, 버전 칼럼처럼 싼 값으로 만들면 DB 한 칸만 읽고 304를 줄 수 있습니다
강한 vs 약한 ETag"abc"는 바이트까지 같음, W/"abc"(weak)는 뜻만 같음. jQuery 파일은 압축해서 받으면 바이트가 달라져 W/가 붙습니다. 304 판단엔 둘 다 됩니다
Last-Modified 방식지문 대신 "마지막으로 고친 시각"으로 묻는 옛 방식(If-Modified-Since). 1초 단위라 1초 안에 두 번 바뀌면 못 잡습니다. 둘 다 있으면 ETag가 우선
If-Match (수정할 때)PUT 요청에 If-Match: "v3"를 붙이면 "내가 본 게 v3일 때만 바꿔 줘". 그사이 누가 바꿨으면 412. 두 사람이 동시에 고쳐 덮어쓰는 걸 막습니다
외우는 법

None-Match는 "안 맞으면 줘"(읽을 때, 결과 304). Match는 "맞을 때만 해"(고칠 때, 실패 412).

UNIT 4 · Q20

서버가 정하는 보관 규칙: 응답의 Cache-Control

응답의 Cache-Control은 서버가 모든 캐시에게 주는 보관 규칙이다. no-cache는 "저장해도 되지만 매번 확인", no-store는 "저장하지 마".

누가 누구에게

서버(개발자)가 응답 헤더에 적고, 그 응답이 지나가는 모든 캐시(CDN, 프록시, 브라우저)가 읽고 따릅니다. 여러 값을 쉼표로 이어 씁니다. 예: Cache-Control: public, max-age=3600.

Q20: no-cache는 "캐시하지 마"가 아니다

no-cache저장 OK, 쓰기 전에 매번 확인

함정 두 개

① "캐시 끄기"라고 no-cache를 넣었는데 개인정보가 디스크에 남는 경우. ② "확실히 하려고" 모든 응답에 no-store를 넣어 304의 이득을 다 버리는 경우. 늘 최신이기만 하면 되는 곳은 no-cache가 더 쌉니다.

UNIT 5

브라우저의 부탁: 요청의 Cache-Control과 새로고침

요청에 실린 Cache-Control은 브라우저가 이번 한 번만 하는 부탁이다. 새로고침할 때 브라우저가 알아서 붙인다.

요청에도 Cache-Control이 있다

단원 4의 Cache-Control은 서버가 "이 응답 이렇게 보관해"라고 적은 것이었습니다. 반대로 브라우저가 요청에 Cache-Control을 붙이기도 합니다. 그때 뜻은 "이번 요청에는 저장된 복사본을 그냥 주지 말고 이렇게 해 줘"입니다. 듣는 쪽은 주로 가는 길의 캐시들(브라우저 자신의 캐시, CDN)이고, 앱 서버는 보통 신경 쓰지 않습니다.

응답의 Cache-Control서버가 적는 보관 규칙

"이 응답은 1시간 보관해도 돼", "공용 캐시는 저장 마". 오래 효력이 있고 모든 캐시가 따른다. 개발자가 서버에서 정한다.

요청의 Cache-Control브라우저가 하는 이번 한 번의 부탁

"이번엔 확인받은 걸로 줘", "이번엔 처음부터 받아 줘". 그 요청 하나에만 해당한다. 보통 브라우저가 새로고침할 때 스스로 붙인다.

  • 요청의 max-age=0: "0초보다 오래된 복사본은 싫어." 모든 복사본은 0초보다 오래됐으니, 결국 "서버에 확인받은 걸로 줘"입니다.
  • 요청의 no-cache: "저장된 복사본을 확인 없이 쓰지 마." 브라우저의 강력 새로고침은 여기에 더해 지문(If-None-Match)도 안 보내서, 결국 처음부터 다 받습니다.
함정 · 같은 no-cache, 다른 뜻

응답에 있으면 "저장해도 되지만 쓸 때마다 확인해"(보관 규칙). 요청에 있으면 "이번엔 저장본을 그냥 주지 마"(한 번의 부탁). 어느 쪽 헤더인지 먼저 보고 뜻을 읽습니다.

새로고침 세 가지

크롬 기준입니다. 다른 브라우저도 큰 틀은 같습니다.

주소창 Enter · 링크 클릭평소대로요청에 붙이는 것 없음

신선한 복사본은 서버에 묻지 않고 그대로 씁니다. 상한 것만 지문 들고 확인.

새로고침 (F5, Cmd+R)페이지는 확인받기Cache-Control: max-age=0

페이지 HTML 요청에 붙여, 신선해도 서버에 확인합니다(304 또는 200). 페이지 안의 그림·JS는 신선하면 그대로.

강력 새로고침 (Ctrl+Shift+R, Cmd+Shift+R)처음부터 다 받기Cache-Control: no-cache

모든 요청에 붙이고 지문도 안 보냅니다. 전부 200으로 새로 받습니다. 옛 헤더 Pragma: no-cache도 같이 붙습니다.

출제 예상
QF5와 Ctrl+Shift+R은 뭐가 달라요? AF5는 브라우저가 페이지 요청에 Cache-Control: max-age=0을 붙여 "확인받은 걸로 줘"라고 합니다. 안 바뀌었으면 304라 빠릅니다. 강력 새로고침은 모든 요청에 no-cache를 붙이고 지문도 빼서, 캐시를 무시하고 전부 새로 받습니다.
쪽집게 · "내 화면에선 되는데요"

남의 화면만 옛것이면 그 사람 캐시에 신선한 복사본이 남아 있는 경우가 많습니다. 확인할 때는 강력 새로고침, 또는 DevTools Network 탭의 Disable cache를 켜고 봅니다. 근본 해결은 서버의 보관 규칙(단원 4·7)을 고치는 것입니다.

UNIT 6 · Q23

같은 주소, 다른 응답: 콘텐츠 협상과 Vary

브라우저가 Accept-* 요청 헤더로 원하는 걸 말하고, 서버가 골라 Content-* 응답 헤더로 알린다. 이게 콘텐츠 협상이다.

왜 필요한가

같은 주소 /를 한국 사람은 한국어로, 미국 사람은 영어로 보고 싶습니다. 같은 그림도 최신 브라우저에는 가벼운 AVIF로, 옛 브라우저에는 JPEG로 주고 싶습니다. 주소는 하나인데 줄 수 있는 내용은 여러 개입니다. 그래서 브라우저가 "나는 이런 걸 원해"를 요청 헤더로 말하고, 서버가 그중 하나를 골라 줍니다. 이걸 콘텐츠 협상(content negotiation)이라고 합니다.

외우는 법 · 카페 주문

"커피 주세요(같은 주소). 따뜻한 걸로, 없으면 아이스도 괜찮아요(Accept)." 점원이 "따뜻한 걸로 드렸어요(Content)"라고 알려 줍니다. 원하는 게 없으면 있는 걸 줍니다.

브라우저가 요청에서버가 응답에예
AcceptContent-Type같은 /orders/7을 앱에는 JSON, 주소창에는 HTML로. 그림을 AVIF·WebP·JPEG 중에서
Accept-LanguageContent-Language한국어 페이지냐 영어 페이지냐
Accept-EncodingContent-Encodinggzip·br로 압축해 줄까. MDN 첫 화면은 119KB가 16.5KB로

Accept-Language: ko-KR,ko;q=0.9,en;q=0.8의 q는 선호도(0~1)입니다. "한국어가 제일, 영어는 차선."

출제 예상 · Q23
Q같은 URL인데 Accept-Language에 따라 한국어·영어 페이지를 돌려주는 것은? A콘텐츠 협상.
  • MDN은 Accept-Language: ko에 302 → /ko/로 답합니다. 같은 주소에서 바로 주지 않고 언어별 주소로 보냅니다. 주소가 나뉘면 캐시·검색·공유 링크가 단순해집니다.
  • GitHub는 ko를 보내도 영어(content-language: en-US)를 줍니다. 협상은 부탁일 뿐, 없으면 기본값을 줍니다.

Vary: 협상하면 캐시가 헷갈린다

캐시는 원래 주소만 보고 "같은 요청이네, 저장해 둔 걸 주자"라고 판단합니다. 그런데 협상을 하면 같은 주소에 한국어판과 영어판이 따로 있습니다. 서버가 응답에 Vary: Accept-Language를 붙이면 캐시는 "주소 + 언어"를 묶어 따로 저장합니다.

함정 · Vary를 빼먹으면

한국인이 먼저 받은 한국어판이 CDN에 저장되고, 다음에 온 미국인도 한국어판을 받습니다. 압축을 못 읽는 프로그램이 압축된 본문을 받기도 합니다. 그래서 거의 모든 사이트에 Vary: Accept-Encoding이 붙어 있습니다(nginx는 gzip_vary on;).

함정 · 너무 많이 붙여도 문제

Vary: User-Agent(브라우저 종류)나 Vary: Cookie처럼 사람마다 값이 다른 헤더를 걸면 복사본이 잘게 쪼개져 거의 다시 쓰이지 않습니다. 캐시가 있으나 마나가 됩니다.

Vary와 private: 같은 질문, 다른 답

둘 다 "같은 주소인데 사람마다 응답이 다를 때, 공용 캐시가 남의 응답을 엉뚱한 사람에게 주지 않게 하려면?"에 대한 답입니다. 응답이 몇 가지로 나뉘느냐에 따라 갈립니다.

Vary응답이 몇 가지 판으로 나뉠 때

한국어판·영어판, 압축판·안 압축판. 판별로 따로 저장하면 됩니다. 한국어판은 다른 한국 사람과 나눠 써도 됩니다.

private응답이 사람마다 하나일 때

내 장바구니, 내 정보. 남과 나눌 일이 없으니 공용 캐시에 아예 넣지 않습니다. 단원 2에서 본 그 private입니다.

쪽집게

판이 몇 개면 Vary, 사람마다 하나면 private. 로그인한 사람마다 다른 화면을 Vary: Cookie로 나눠 보려 하면, 사람 수만큼 복사본이 생겨 아무도 다시 안 쓰고 설정을 하나만 틀려도 남의 화면이 갑니다.

실무에서는: 무엇을 얼마나 오래 캐시하나

내용이 바뀌면 이름도 바뀌는 파일은 길게, 이름은 그대로인데 내용이 바뀌는 HTML·API는 짧게 + ETag.

파일 이름에 지문 붙이기

React·Vue 앱을 빌드하면 index-3f9a1c.js처럼 파일 이름에 이상한 글자가 붙습니다. 내용으로 만든 지문(해시)입니다. 코드를 고치면 이름이 index-8b21d0.js로 바뀝니다.

  • 그래서 이 파일들은 1년 캐시해도 안전합니다. 내용이 바뀌면 아예 다른 이름이 되니, 옛 복사본을 쓸 일이 없습니다.
  • 대신 그 이름들을 적어 둔 index.html은 no-cache로 둡니다. 그래야 배포하자마자 새 이름을 압니다.
쪽집게 · "배포했는데 화면이 안 바뀐다"

대개 index.html에 긴 캐시가 걸렸거나 CDN이 HTML을 들고 있는 경우입니다. 먼저 curl -sI 주소 | grep -i cache-control로 HTML의 보관 규칙부터 봅니다.

UNIT 8 · 지난주

지난주 과제 C와 이어지는 곳

같은 멱등 키로 두 번 보내도 주문은 1건이었고, 500은 앱이, 502·504는 앞에 선 nginx가 만들었다.

과제 C는 주문 API 앞에 nginx(요청을 받아 뒤의 앱 서버에 넘겨 주는 문지기, 리버스 프록시)를 두고, 일부러 장애를 내 본 것입니다.

  • 멱등 키: 같은 주문 요청이 재시도로 두 번 와도, 요청에 붙은 Idempotency-Key가 같으면 주문을 한 번만 만들고 처음 응답을 다시 돌려줍니다. 키는 클라이언트가 "주문 버튼을 누른 한 번"마다 만듭니다.
  • 500: 앱이 스스로 에러를 냄. 502·504: nginx가 뒤의 앱과 통하지 못해 대신 냄.
502 Bad Gateway거절당했다

앱 프로세스가 죽어 컴퓨터(OS)가 "여기 아무도 없어요"라고 바로 거절하거나, 앱이 응답 도중에 끊었을 때.

504 Gateway Timeout대답이 없다

앱이 너무 오래 걸리거나, 앱 컨테이너가 통째로 사라져 거절해 줄 OS조차 없어 기다리다 시간 초과.

외우는 법

거절은 502, 침묵은 504.

  • nginx는 연결이 우연히 끊기면 GET은 몰래 한 번 더 보내고, POST는 보내지 않습니다. 두 번 보내도 안전한 요청만 재시도합니다.
  • 504가 나도 앱은 일을 계속합니다. nginx만 기다리기를 포기한 것입니다.
오늘 주제로 넘어가는 다리

멱등 키 저장소도, 캐시도 "같은 요청엔 저장해 둔 응답"입니다. 다른 건 누가 저장하느냐(서버 vs 브라우저·CDN)와 언제까지 믿느냐(키 24시간 vs max-age)입니다.

  2. 응답의 no-cache는 저장하되 매번 확인, no-store는 저장 금지. (Q20)
  3. If-None-Match로 물었는데 그대로면 304, 본문 없음. 304는 본문만 아낀다. (Q21)
  4. 같은 주소에서 Accept-*로 골라 주는 건 콘텐츠 협상. 공용 캐시가 판을 섞지 않게 Vary를 붙인다. (Q23)
  5. Cache-Control은 응답에선 서버의 보관 규칙, 요청에선 브라우저의 한 번 부탁(새로고침).
