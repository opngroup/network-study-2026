### 장표 2 · 멱등 API를 만들고, 5xx를 일부러 냈다

**한 줄로**: 같은 키로 두 번 보내도 주문은 1건이었고, 500은 앱이, 502·504는 nginx가 만들었다.

| 한 일 | 결과 |
| --- | --- |
| ① 같은 `Idempotency-Key`로 `POST /orders` 두 번 | 둘 다 201, 두 번째는 `Idempotent-Replayed: true`. 주문 1건 |
| ② `/boom`(예외), `/slow?ms=4000`(nginx는 2초만 기다림) | 500 JSON(0.000초), 504 HTML(정확히 2.00초) |
| ③ 느린 POST가 504 → 같은 키로 재시도 | 재시도는 저장된 201. 주문이 두 번 생기지 않음 |
| ④ `/crash`(응답 도중 끊기), 앱을 127.0.0.1에 바인딩 | 둘 다 즉시 502 |

### 장표 3 · 해 보고 알게 된 것

**한 줄로**: "거절당하면 502, 대답이 없으면 504"이고, nginx는 GET을 몰래 재시도하며, 504가 나도 앱은 일을 계속한다.

1. **앱 컨테이너를 통째로 끄면 504가 났다.** 컨테이너가 멈추면 그 IP가 사라져서, nginx의 SYN에 "여기 없어요"(RST)라고 답해 줄 OS조차 없습니다. SYN이 허공에 떨어지고 `proxy_connect_timeout`(2초)이 지나 504가 됩니다. 반대로 OS는 살아 있는데 포트를 듣는 프로세스가 없으면 OS가 즉시 RST로 거절해서 502입니다. 진단 퀴즈 Q17("앱 서버 **프로세스**가 죽으면?" → 502)은 그대로 맞습니다. 프로세스만 죽은 것과 기계째 사라진 것이 다를 뿐입니다.
2. **nginx가 GET을 한 번 더 보냈다.** 로그에 `upstream_status=502, 502`. upstream `keepalive`로 재사용하던 연결이 끊기자 nginx가 새 연결로 다시 보낸 것입니다. `keepalive`를 빼고 해 보니 재시도가 사라졌습니다. POST(④의 느린 주문)는 다시 보내지 않았습니다. 3주차에 말한 "nginx도 멱등 요청만 재시도한다"를 직접 봤습니다.
3. **504가 나도 앱은 일을 계속한다.** nginx는 2초에 포기했지만 앱 로그에는 "4000ms 끝, 응답 보냄"이 찍혔습니다. `proxy_read_timeout`만 줄이면 사용자는 빨리 실패를 보지만, 서버는 받을 사람 없는 일을 계속합니다.
4. **오늘 주제로 넘어가는 다리.** 멱등 키 저장소는 "같은 요청이 오면 저장해 둔 응답을 준다"였습니다. 캐시도 똑같이 "같은 요청엔 저장된 응답"입니다. 차이는 **누가 저장하느냐(서버 vs 브라우저·CDN)와 언제까지 믿느냐(키 24시간 vs max-age)** 입니다.

**이런 질문을 받으면**

- *그럼 장애 때 502와 504 중 뭐가 뜨는지로 원인을 못 가르나?* 대략은 가를 수 있습니다. 502는 "갔는데 거절당했거나 이상한 답", 504는 "기다렸는데 답이 없음"입니다. 다만 504도 `while connecting`(연결 자체가 안 됨)과 `while reading response header`(연결은 됐는데 답이 늦음)로 나뉘니, nginx error.log의 그 문구까지 봐야 정확합니다.
- *nginx 재시도를 끄려면?* `proxy_next_upstream off;`. 다만 keepalive 연결이 우연히 닫힌 경우를 살려 주는 재시도라 보통은 그대로 둡니다. 위험한 건 POST 재시도인데, 그건 기본으로 꺼져 있습니다(`non_idempotent`를 붙여야 켜짐).

### 장표 5 · 응답을 저장해 두는 곳은 여러 군데다

**한 줄로**: 브라우저(나만), CDN·프록시(모두 같이)가 응답을 저장하고, 요청은 가까운 곳에 있으면 거기서 멈춘다.

- **private 캐시**: 브라우저 캐시. 내 냉장고입니다. 내 장바구니처럼 나에게만 맞는 응답도 여기엔 둬도 됩니다.
- **shared 캐시**: CDN(Cloudflare, CloudFront), 설정한 nginx. 동네 마트 진열대입니다. 한 사람이 받은 응답을 다른 사람에게도 줍니다. 그래서 **개인 정보가 담긴 응답이 여기에 들어가면 사고**입니다. `Cache-Control: private`로 막습니다.
- 오늘 MDN을 받았을 때 `x-cache: MISS, HIT, HIT` 헤더가 보였습니다. CDN 안에서도 여러 층을 거치며 어디서 꺼냈는지를 알려 주는 것입니다.

### 장표 6 · 저장한 응답에는 유통기한이 있다

**한 줄로**: `max-age` 동안은 신선(fresh)해서 묻지 않고 쓰고, 지나면 상한(stale) 것이라 확인을 거친다.

- `max-age=3600`: 받은 때부터 3600초 동안 신선합니다.
- `Age: 1254`: shared 캐시가 이 응답을 들고 있은 시간입니다. 그래서 내 브라우저 입장에서 남은 신선 시간은 3600 − 1254초입니다. CDN에서 받은 응답은 "갓 만든" 게 아닐 수 있다는 뜻입니다.
- `max-age`가 없으면? 브라우저는 `Last-Modified`를 보고 "수정된 지 오래된 파일이면 좀 더 써도 되겠지" 하고 스스로 기한을 추측합니다(휴리스틱 캐시). 예상 못한 캐시가 생기는 흔한 원인이라, **API 응답에는 Cache-Control을 명시**하는 게 좋습니다.

### 장표 7 · 캐시가 하는 판단은 세 갈래다

**한 줄로**: 신선하면 바로 쓰고, 상했는데 지문이 있으면 물어보고(304), 지문도 없으면 다시 받는다(200).

- DevTools Network 탭에서 Size 열에 `(memory cache)`나 `(disk cache)`가 보이면 첫 번째 경우입니다. 서버 로그에도 안 남습니다. "배포했는데 사용자 화면이 안 바뀌어요"의 단골 원인입니다.
- 304가 보이면 두 번째 경우입니다. 요청은 나갔지만 본문은 안 받았습니다.

**이런 질문을 받으면**

- *새로고침(F5)하면?* 브라우저는 신선한 것도 재검증합니다(요청에 `Cache-Control: max-age=0`을 붙여 보냄). 강력 새로고침(Ctrl+Shift+R)은 캐시를 무시하고 처음부터 받습니다(`no-cache`를 붙여 보냄). 그래서 "내 화면에선 되는데요"를 확인할 때 일반 새로고침과 강력 새로고침 결과가 다를 수 있습니다.

## 본론 (장표 8~14)

### 장표 8 · Q20: no-cache는 "저장 금지"가 아니다

**한 줄로**: `no-cache`는 저장하되 매번 확인, `no-store`는 저장 금지.

이름이 오해를 부릅니다. `no-cache`는 "캐시된 걸 확인 없이 쓰지 마"라는 뜻이라, 사실상 `max-age=0`에 재검증 필수를 더한 것입니다.

- **no-cache가 맞는 곳**: 항상 최신이어야 하지만 자주 바뀌지는 않는 것. 예: SPA의 `index.html`. 매번 묻되, 안 바뀌었으면 304로 본문을 아낍니다.
- **no-store가 맞는 곳**: 디스크에 남으면 안 되는 것. 예: 계좌 내역, 개인정보 화면, 1회용 토큰 응답. 공용 PC에서 뒤로 가기를 눌러도 남지 않게 합니다.
- **함정**: "캐시 끄기"라고 `no-cache`를 넣었는데 화면에 개인정보가 디스크에 남는 경우, 반대로 "확실히 하려고" 모든 응답에 `no-store`를 넣어 304의 이득을 다 버리는 경우가 흔합니다.

**이런 질문을 받으면**

- *네이버는 왜 `no-cache, no-store, must-revalidate`를 다 넣었나?* 오래된 브라우저·프록시가 일부 지시어를 모를 때를 대비한 "허리띠와 멜빵" 방식입니다. 셋 중 실제로 이기는 건 `no-store`입니다.
- *`Pragma: no-cache`는?* HTTP/1.0 시절 헤더입니다. 지금은 `Cache-Control`만 쓰면 됩니다.

### 장표 9 · 자주 쓰는 Cache-Control 값 여덟 개

**한 줄로**: 기한(`max-age`, `s-maxage`), 누가(`public`, `private`), 확인 방식(`no-cache`, `must-revalidate`), 저장 금지(`no-store`), 최적화(`immutable`, `stale-while-revalidate`).

- `s-maxage`는 CDN에만 다른 기한을 주고 싶을 때 씁니다. 예: 브라우저는 60초, CDN은 1시간(`max-age=60, s-maxage=3600`). 배포 때 CDN만 지우면(purge) 됩니다.
- `must-revalidate`는 "상한 걸 쓰지 마"입니다. 원본 서버가 죽었을 때 캐시가 상한 걸 몰래 주는 걸 막고, 대신 504를 줍니다. 3주차와 이어지는 지점입니다.
- `immutable`은 신선 기간 안에 사용자가 새로고침해도 재검증하지 말라는 뜻입니다. `app.3f9a1c.js`처럼 내용이 바뀌면 파일 이름이 바뀌는 파일에만 씁니다.
- `stale-while-revalidate=N`은 상한 뒤 N초까지는 일단 옛것을 즉시 주고 뒤에서 새로 받아 둡니다. 사용자 체감 속도가 좋아집니다. React의 SWR 라이브러리 이름이 여기서 왔습니다.

### 장표 10 · Q21: ETag → If-None-Match → 304

**한 줄로**: 서버가 지문(ETag)을 주고, 브라우저가 그 지문을 들고 다시 물으면, 안 바뀌었을 때 304와 빈 본문이 온다.

1. 첫 요청: 서버가 `200`, `ETag: "v3"`, 본문을 보냅니다. 브라우저가 셋을 같이 저장합니다.
2. 신선 기간이 지난 뒤: 브라우저가 `If-None-Match: "v3"`를 붙여 같은 주소로 요청합니다.
3. 서버가 지금 지문을 계산해 비교합니다. 같으면 `304 Not Modified`(본문 없음), 다르면 `200`과 새 ETag·새 본문.

- **ETag 만드는 법**: 본문의 해시(sha1 등), DB 행의 `updated_at`이나 버전 번호. 과제 D에서 주문 응답에 붙여 봅니다.
- **강한 ETag와 약한 ETag**: `"abc"`는 바이트까지 같음, `W/"abc"`는 의미가 같음(압축 방식 차이 등은 무시). 오늘 GitHub와 jQuery CDN이 `W/`를 썼습니다. 304 판단에는 둘 다 쓸 수 있습니다.
- **Last-Modified / If-Modified-Since**: 지문 대신 "마지막 수정 시각"으로 묻는 옛 방식입니다. 1초 단위라 1초 안에 두 번 바뀌면 못 잡고, 둘 다 있으면 ETag가 우선합니다.
- **304도 공짜는 아니다**: 요청과 왕복은 그대로 듭니다. 서버도 지문을 계산하려고 DB를 읽을 수 있습니다. 아끼는 건 본문 전송입니다.

**이런 질문을 받으면**

- *서버가 304를 주려면 결국 데이터를 다 읽어야 하지 않나?* 본문 해시로 ETag를 만들면 그렇습니다. 그래서 `updated_at`이나 버전 컬럼처럼 싸게 얻는 값으로 ETag를 만들면 DB에서 그 한 칸만 읽고 304를 줄 수 있습니다.
- *ETag가 PUT에도 쓰이나?* 네. `If-Match: "v3"`를 붙여 PUT하면 "내가 본 게 v3일 때만 바꿔 줘"가 됩니다. 그사이 누가 바꿨으면 412 Precondition Failed. 두 사람이 동시에 수정할 때 덮어쓰기를 막는 방법(낙관적 잠금)이고, 3주차 409·멱등성 이야기와도 이어집니다.

### 장표 11 · 직접 보기: MDN 117KB가 0바이트로

**한 줄로**: 같은 주소를 ETag를 들고 다시 물었더니 304, 본문 0바이트였다.

발표 때 터미널에서 그대로 보여 줍니다.

```bash
# ① 처음 받기: ETag와 크기 확인
curl -s -o /dev/null -D - -w 'body=%{size_download}B\n' https://developer.mozilla.org/en-US/ \
  | grep -iE '^(HTTP|etag|cache-control|age)|body'

# ② 받은 ETag를 넣어 다시 묻기 (값은 ①에서 복사)
curl -s -o /dev/null -D - -w 'body=%{size_download}B\n' \
  -H 'If-None-Match: "여기에 ETag"' https://developer.mozilla.org/en-US/ \
  | grep -iE '^(HTTP|etag)|body'
```

오늘(11/12) 오전에 잰 값: ① `200`, 본문 116,977 B(gzip 요청 시 16,430 B), `cache-control: public, max-age=3600` ② `304`, 본문 0 B, 0.03초.

- MDN 문서가 그사이 바뀌면 ETag가 달라져서 ②가 200이 됩니다. 그러면 "바뀌었으니 새로 받았다"는 것도 좋은 시연입니다.
- 브라우저로 보여 주려면 DevTools Network 탭에서 같은 페이지를 일반 새로고침(F5)합니다. 문서 요청이 304로 보입니다.

### 장표 12 · Q23: 같은 주소, 다른 응답: 콘텐츠 협상

**한 줄로**: 브라우저가 `Accept-*` 헤더로 원하는 것을 말하고, 서버가 골라서 `Content-*` 헤더로 무엇을 골랐는지 알린다.

| 브라우저 → | ← 서버 | 실무 예 |
| --- | --- | --- |
| `Accept: application/json` | `Content-Type: application/json` | 같은 `/orders/7`을 API는 JSON, 브라우저 주소창은 HTML로 |
| `Accept: image/avif,image/webp,*/*` | `Content-Type: image/avif` | 이미지 CDN이 브라우저가 지원하는 가장 가벼운 형식으로 |
| `Accept-Language: ko-KR,ko;q=0.9,en;q=0.8` | `Content-Language: ko` | 다국어 사이트 |
| `Accept-Encoding: gzip, br` | `Content-Encoding: br` | 압축. MDN은 117KB가 gzip으로 16KB |

- `q=0.9`는 선호도(0~1)입니다. "한국어 제일, 영어는 차선"이라는 뜻입니다.
- 오늘 MDN 첫 주소(`/`)에 `Accept-Language`만 바꿔 보냈더니 ko → `/ko/`, ja → `/ja/`, en → `/en-US/`로 302 리다이렉트했습니다. 협상 결과를 같은 주소에서 바로 주지 않고, 언어별 주소로 보내는 방식입니다. 언어별로 주소가 다르면 캐시·검색 엔진·공유 링크가 단순해져서 이 방식을 많이 씁니다.
- GitHub는 `Accept-Language: ko`를 보내도 `content-language: en-US`였습니다. 협상은 "요청"일 뿐이고, 서버가 그 언어를 안 갖고 있으면 기본값을 줍니다.

### 장표 13 · Vary: 캐시에게 "이 헤더도 보고 구분해"

**한 줄로**: 협상하는 응답에는 `Vary`로 "어떤 요청 헤더에 따라 달라지는지" 적어야 shared 캐시가 섞지 않는다.

- 캐시의 기본 열쇠는 주소(정확히는 메서드 + URL)입니다. `Vary: Accept-Language`가 있으면 열쇠에 그 헤더 값이 더해집니다.
- 거의 모든 사이트에 `Vary: Accept-Encoding`이 있습니다. 압축 응답을 압축 못 읽는 클라이언트에 주지 않기 위해서입니다. nginx `gzip_vary on;`이 이걸 붙여 줍니다.
- **Vary를 너무 많이 붙이면** 캐시가 잘게 쪼개져 거의 안 맞습니다. GitHub처럼 열 개 넘게 붙인 응답은 사실상 shared 캐시에 넣을 생각이 없는 것이고, 실제로 `private`입니다. `Vary: Cookie`, `Vary: User-Agent`도 같은 이유로 CDN 적중률을 망칩니다.
- **로그인 사용자별 응답은 Vary가 아니라 `private`로 막습니다.** `Vary: Authorization`으로 버티는 것보다 shared 캐시에 아예 안 넣는 쪽이 안전합니다.

**이런 질문을 받으면**

- *MDN 리다이렉트 응답의 Vary는?* 오늘 `Accept-Language: ko`로 받은 302 응답 헤더를 보면 `vary: Accept`만 있고 `Accept-Language`는 없었습니다. `cache-control: max-age=3600, public`이라 헤더만 보면 shared 캐시가 `/ko/` 리다이렉트를 다른 언어 사용자에게 줄 수 있는 모양입니다. 실제로는 CDN 설정에서 따로 처리하고 있을 것으로 보입니다(밖에서는 확인 불가). "Vary를 빠뜨리기 쉽다"는 예로만 쓰고, MDN이 틀렸다고 단정하지는 않습니다.

### 장표 14 · 사이트마다 정책이 다르고, 다 이유가 있다

**한 줄로**: 내용이 바뀌면 주소가 바뀌는 파일은 길게, 주소는 그대로인데 내용이 바뀌는 HTML·API는 짧게 + ETag.

오늘(11/12) 받은 헤더입니다.

| 무엇 | Cache-Control | 읽는 법 |
| --- | --- | --- |
| 네이버 첫 화면 | `no-cache, no-store, must-revalidate` | 로그인·개인화 화면이라 아예 남기지 않음. ETag도 없다 |
| GitHub 첫 화면 | `max-age=0, private, must-revalidate` + `ETag: W/"…"` | 나만 저장, 매번 확인, 안 바뀌었으면 304 |
| MDN 문서 | `public, max-age=3600` + ETag | 누구에게나 같은 문서. CDN이 1시간 들고 있음(`age` 헤더) |
| jQuery 3.7.1 | `public, max-age=31536000, stale-while-revalidate=604800` | 주소에 버전(3.7.1)이 있어 내용이 절대 안 바뀜 → 1년 |
| example.com | Cache-Control 없음, `Last-Modified`만 | 브라우저가 기한을 추측하는 휴리스틱 캐시 대상 |

- 프론트 빌드 도구(Vite, webpack, Next.js)가 파일명에 해시(`index-3f9a1c.js`)를 붙이는 이유가 이것입니다. 내용이 바뀌면 이름이 바뀌니 1년 캐시를 걸어도 안전합니다. 대신 그 파일을 가리키는 `index.html`은 `no-cache`로 둬야 새 이름을 바로 압니다.
- "배포했는데 사용자 화면이 안 바뀐다"는 대개 `index.html`에 긴 캐시가 걸렸거나 CDN이 HTML을 들고 있는 경우입니다.

### 장표 15 · 정리

한 문장으로 묶으면: "신선하면 그냥 쓰고, 상하면 지문 들고 묻고, 내 것이면 private, 같은 주소에 다른 걸 주면 Vary."

그다음 "우리 서비스에서는" 박스를 실제 확인 결과로 채워서 말합니다.

- [ ] 우리 API 응답 하나를 `curl -I`로 받아 `Cache-Control`이 있는지 확인 (없으면 휴리스틱 캐시 대상)
- [ ] 로그인한 사용자 정보 API에 `private` 또는 `no-store`가 있는지 확인
- [ ] 프론트 번들 파일명에 해시가 있는지, 그 파일의 `Cache-Control`이 긴지, `index.html`은 `no-cache`인지
- [ ] CDN을 쓴다면 HTML을 캐시하는지, 배포 때 무엇을 비우는지(purge)
- [ ] 확인 결과를 장표 15의 대괄호 자리에 채우기

### 과제 C 데모 순서

미리 `cd week-03/유진영/assignment-c && docker compose up -d --build` 해 둡니다(이미지 받는 데 시간이 걸릴 수 있음).

1. **멱등**: 같은 키로 두 번 보내고 `GET /orders`가 1건인 것
   ```bash
   for i in 1 2; do curl -si -X POST localhost:8080/orders -H 'content-type: application/json' \
     -H 'Idempotency-Key: demo-1' -d '{"item":"coffee","qty":1}' | grep -iE '^(HTTP|idempotent)'; done
   curl -s localhost:8080/orders
   ```
2. **500 vs 504를 본문으로 구분**: `curl -i localhost:8080/boom`(JSON) → `curl -i 'localhost:8080/slow?ms=4000'`(2초 뒤 nginx HTML)
3. **504의 함정**: `?delayMs=4000`으로 POST → 504 → 같은 키로 다시 → `Idempotent-Replayed: true`
4. **예상과 달랐던 것**: `docker compose stop app` 뒤 `curl -i localhost:8080/health` → 2초 뒤 504. "왜 502가 아닐까?" 하고 질문을 던진 뒤 설명
5. **nginx 로그**: `docker compose logs nginx | grep -E 'error|status=5'`로 `upstream_status=502, 502`와 `while connecting` 보여 주기
6. 끝나면 `docker compose down`

시간이 모자라면 `bash reproduce.sh`(약 25초)를 한 번 돌리고 `capture/repro-output.txt`를 보여 줍니다.

### 과제 C에서 받을 만한 질문

- *멱등 키는 누가 만드나?* 클라이언트가 만듭니다. "사용자가 주문 버튼을 누른 그 한 번"마다 UUID를 하나 만들고, 그 요청을 재시도할 때는 같은 키를 씁니다. 버튼을 다시 누르는 건 새 주문이니 새 키입니다.
- *메모리 저장소면 서버 2대일 때는?* 깨집니다. 첫 요청은 1번 서버, 재시도는 2번 서버로 가면 2번 서버는 키를 모릅니다. 7주차에 Redis를 붙일 때 같이 옮기면 좋습니다(`SET key "processing" NX EX 86400`).
- *처리 중(409)일 때 클라이언트는?* 잠깐 기다렸다 같은 키로 다시 보내면 됩니다. 첫 요청이 끝났으면 그 결과를 받습니다. `Retry-After` 헤더를 붙여 주면 더 친절합니다.
