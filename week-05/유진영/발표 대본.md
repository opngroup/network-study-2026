## 장표별 대본

### 1 · 표지 (15초)

**"오늘은 HTTP가 왜 서버 쪽에서 먼저 말을 못 하는지부터 시작해서, WebSocket 연결이 어떻게 시작되고 연결된 뒤 선 위에 실제로 뭐가 지나가는지 바이트까지 보겠습니다."**

### 2 · 과제 D 1/2 (45초)

- **"주문 하나에 ETag를 붙였더니, 같은 지문으로 다시 물으면 304에 본문 0바이트가 왔습니다."**
- 세 칸을 짚으며: 200 → 304 · PATCH 하면 지문이 바뀌고 옛 지문으로 고치려 하면 412 · 네 사이트 문서는 모두 h2, GitHub 정적 파일은 h2·h3가 섞임.

### 3 · 과제 D 2/2 (1분)

- 01: **"nginx에서 gzip을 켜면 ETag가 W/로 바뀝니다. 압축하면 바이트가 달라지니 강한 지문을 약한 지문으로 낮추는 거예요. 304는 오지만 If-Match에 쓰면 412가 납니다."**
- 02·03은 한 줄씩: "304에도 ETag·Cache-Control은 실어야 한다", "다른 출처 파일은 Protocol이 빈칸, 빈칸은 h1이 아니라 모름".
- 04 (다리): **"캐시와 ETag는 브라우저가 물을 때 덜 보내는 법이었죠. 오늘은 브라우저가 묻지 않아도 보내는 법입니다."**

### 4 · 퀴즈 다시 풀기 (40초)

- 답을 가리고 문제만 읽습니다. 주영님께: "WebSocket은 HTTP랑 상관없는 별도 연결 맞죠?" (대부분 "네" → 오늘 뒤집을 포인트)
- **"답은 'HTTP 요청에 Upgrade를 붙이고, 서버가 101로 답한다'입니다. 오늘은 왜 HTTP로 시작하는지, 101 뒤엔 뭐가 오가는지까지 갑니다."**

### 5 · HTTP는 물어야 답한다 (1분)

- 흐름을 위에서 아래로: 묻고 → 답하고 끝 → 친구가 보냄 → 다시 물어야 받음.
- **"서버는 새 메시지가 온 걸 알아도, 브라우저가 다시 묻기 전엔 전할 방법이 없습니다."**
- **"HTTP는 무전기, WebSocket은 전화입니다. 그런데 아래 TCP 연결은 원래 양방향이에요. 막고 있는 건 HTTP라는 대화 규칙입니다."**
- 덧붙이면: 서버가 먼저 브라우저에 연결하는 건 NAT 때문에 안 된다(1주차). 그래서 시작은 언제나 브라우저.

### 6 · 누가 보내나 (1분)

- **"Key는 브라우저가 내는 문제, Accept는 서버가 내는 정답입니다. 지난주 Accept-Language는 요청이었는데, Sec-WebSocket-Accept는 응답이에요. 이름에 속지 마세요."**
- 주황 줄: **"101은 이 연결의 마지막 HTTP 응답입니다."**
- 마지막 줄: 프레임은 양쪽 다, 아무 때나.

### 7 · WebSocket이 뭔가 (1분)

- **"WebSocket은 HTTP로 인사한 뒤 같은 TCP 연결을 계속 열어 두고, 양쪽이 아무 때나 메시지를 보내는 규칙입니다."**
- 왜 셋: 서버가 먼저 / 머리 2~14바이트 / 양방향이 잦은 일.
- 주황 상자: **"대신 자동 재연결이 없습니다. HTTP가 해 주던 걸 직접 챙겨야 해요."**

### 8 · 세 방식 비교 (40초)

- **"양쪽이 자주 말하면 WebSocket, 알림만 내려보내면 SSE가 더 단순합니다."** 자세한 건 주영님 발표로 넘깁니다.

### 9 · Q32 핸드셰이크 (1분 20초)

- 왼쪽 상자를 위에서 아래로: **"평범한 GET입니다. 다른 건 Upgrade, Connection, Key, Version 네 줄뿐."**
- 응답: **"성공은 101 하나뿐이고, 본문이 없습니다. 빈 줄 다음부터는 HTTP가 아니라 프레임이에요."**
- **"TV는 그대로, 채널만 돌린다."**

### 10 · Key와 Accept (1분)

- 계산식을 짚고: **"키 뒤에 RFC에 박힌 고정 문자열을 붙여 SHA-1, base64. 데모에서 직접 계산해 보겠습니다."** (데모는 장표 18에서 같이 해도 됨)
- **"이건 보안이 아닙니다. 계산법이 공개돼 있어요. 상대가 WebSocket을 진짜 아는 서버인지 확인하는 장치입니다."**

### 11 · 얻는 것, 거절당하는 모습 (40초)

- 왼쪽: **"HTTP로 시작하니 80·443, nginx, 쿠키, TLS를 그대로 씁니다."**

### 12 · 프레임 (50초)

- **"101 뒤로는 프레임만 오갑니다. 메시지는 편지, 프레임은 봉투예요."**
- 머리 칸을 왼쪽부터: FIN(마지막 조각?), opcode(종류), MASK(가면?), 길이.

- **"81은 FIN=1에 text, 82는 가면 씀에 길이 2. 그 뒤 4바이트가 가면 키, 마지막 두 바이트가 가면 쓴 Hi입니다."**
- 서버 쪽: **"서버가 보낸 건 가면이 없어서 머리가 딱 2바이트입니다. HTTP 요청이면 헤더만 수백 바이트예요."**

- **"TCP는 프레임 경계를 모릅니다. 반쪽만 올 수도, 두 개가 붙어 올 수도 있어서 받는 쪽이 길이를 보고 직접 셉니다."**

### 15 · 마스킹 (1분)

- **"가면은 브라우저가 보내는 프레임만 씁니다. Client Masks."**

### 17 · close (50초)

- **"끝낼 때는 close를 주고받고 TCP를 닫습니다. 03 e8이 1000, 정상 종료."**

### 18 · 라이브 데모 (1분 50초)

```bash
bash demo.sh accept      # 오른쪽 터미널: Key → Accept 계산 (RFC 답과 같은지)
bash demo.sh handshake   # curl로 101, Upgrade 없으면 426, 남의 출처면 403
# 왼쪽 터미널에서는 이미 bash demo.sh server 가 떠 있음
```

1. `accept`: **"openssl로 계산한 값이 RFC 예시와 똑같습니다."**
2. 브라우저 페이지에서 글을 보내고, 왼쪽 서버 터미널을 가리킵니다: **"← 81 8x … MASK=1, 가면 쓴 글. → 81 … MASK=0, 서버가 돌려보낸 글."**
3. DevTools Network: **"WebSocket 줄은 하나뿐이고 상태는 101. 메시지를 백 번 보내도 줄은 안 늘어납니다."** Messages 탭에서 위·아래 화살표.
4. 서버 터미널에 `공지입니다` 치고 엔터: **"브라우저는 아무것도 안 물었는데 떴습니다. 이게 오늘의 핵심입니다."**
5. (시간 있으면) 15초 기다려 서버 로그의 ping → pong. "닫기" 버튼 → close 1000 주고받기.

**데모가 안 될 때**: 장표 18 오른쪽의 캡처된 로그로 같은 이야기를 합니다. 포트가 겹치면 `PORT=9000 bash demo.sh server`(브라우저 주소도 9000). 그래도 안 되면 `cd ws-demo && npm test`로 시험 18개가 통과하는 걸 보여 주고 넘어갑니다.

## 막혔을 때 붙잡을 문장 다섯 개

1. HTTP는 물어야 답한다. WebSocket은 **한 번 연결해 두고 양쪽이 아무 때나** 보낸다.
2. 시작은 **Upgrade: websocket HTTP 요청 → 101**, 그다음 같은 TCP에서 프레임. (Q32)
3. **Accept = Key + 고정 문자열 → SHA-1 → base64.** 보안이 아니라 "WebSocket 아는 서버" 증명.
4. 프레임 머리는 **FIN · opcode · MASK · 길이**. 1 text, 2 binary, 8 close, 9 ping, A pong. **클라이언트만 가면.**
5. **ping엔 pong, 끝낼 땐 close 1000. 1006은 close 없이 끊긴 것.** 다시 붙는 건 내 몫.
