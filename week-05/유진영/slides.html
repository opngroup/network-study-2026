주문 API에 ETag를 붙이고, 사이트 프로토콜을 쟀다

① ETag → 304
같은 지문이면 본문 0바이트

처음 GET은 200, 본문 71바이트, ETag: "ff40…". 그 지문을 If-None-Match에 실으면 304, 본문 0바이트. Cache-Control: private, no-cache.

② 고치면 지문도 바뀐다
옛 지문으로 고치기 = 412

PATCH 하면 ETag가 "5a8c…"로 바뀌고 옛 지문 GET은 200. 옛 지문을 If-Match에 실어 PATCH 하면 412, 주문은 그대로.

③ 프로토콜 표
네 사이트 문서 모두 h2

네이버·GitHub·MDN·jQuery 문서는 h2. GitHub 정적 파일은 한 페이지 안에서 h2와 h3가 섞여 나왔다. 브라우저 nextHopProtocol로 두 번씩 잼.

WebSocket은 HTTP로 인사한 뒤 같은 TCP 연결을 계속 열어 두고, 브라우저와 서버가 아무 때나 서로 메시지를 보내는 규칙. (RFC 6455, ws:// 80 · wss:// 443)
왜 ①
서버가 먼저 말한다

새 채팅, 주문 상태, 남의 커서를 생기는 즉시.

왜 ②
짧은 메시지가 가볍다

프레임 머리 2~14바이트. HTTP 요청은 헤더만 수백 바이트.

왜 ③
양방향이 잦은 일

채팅, 게임, 공동 편집.

대신: 연결을 계속 붙잡고(서버 여러 대면 어디 붙었나), 중간 장비가 말 없는 연결을 끊고, 상태 코드·캐시·자동 재연결이 없다.
서버가 먼저 보내는 세 방법

양쪽이 자주 말하면 WebSocket, 알림만이면 SSE

방식모양방향끊기면
롱 폴링새 소식 생길 때까지 답을 미루는 HTTP서버 → 브라우저받자마자 다시 요청
SSE끝나지 않는 HTTP 응답에 이어 쓰기서버 → 브라우저EventSource가 알아서 재연결
WebSocketHTTP에서 갈아탄 통로. 101 뒤로는 HTTP 아님양방향내 코드가 다시 연결

Upgrade 요청 → 101, 그다음부터 프레임

요청 · 브라우저 → 서버GET /ws HTTP/1.1 Host: localhost:8081 Upgrade: websocket Connection: Upgrade Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ== Sec-WebSocket-Version: 13 응답 · 서버 → 브라우저HTTP/1.1 101 Switching Protocols Upgrade: websocket Connection: Upgrade Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo= (빈 줄 뒤로는 HTTP가 아니라 프레임)

정리: 이 다섯 줄

  1. HTTP는 물어야 답한다. WebSocket은 한 번 연결해 두고 양쪽이 아무 때나 보낸다.
  2. 시작은 Upgrade: websocket HTTP 요청, 서버가 101로 답하면 같은 TCP에서 프레임. (Q32)
  3. Accept = Key + 고정 문자열 → SHA-1 → base64. 보안이 아니라 "WebSocket 아는 서버" 증명.
  4. 프레임 머리는 FIN · opcode · MASK · 길이. 1 text, 2 binary, 8 close, 9 ping, A pong. 클라이언트만 가면.
  5. ping엔 pong, 끝낼 땐 close 1000. 1006은 close 없이 끊긴 것, 다시 붙는 건 내 몫.
