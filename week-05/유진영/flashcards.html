WebSocket: 핸드셰이크와 프레임을 처음부터

채팅 앱에서 친구가 보낸 말이 새로고침 없이 바로 뜨는 이유가 오늘 주제입니다. 끝까지 읽으면 세 가지에 답할 수 있습니다. 보통 HTTP로는 왜 서버가 먼저 말을 못 하나, WebSocket 연결은 어떻게 시작되나(Q32), 연결된 뒤에는 무엇이 오가나(프레임, ping·pong, close).

용어는 처음 나올 때 다 풀어 씁니다. 단원 1은 바탕이 되는 "HTTP는 묻고 답하면 끝" 이야기라, 이미 알아도 표 하나는 꼭 보고 가세요. 상자 읽는 법: 쪽집게는 꼭 외울 것, 함정은 다들 헷갈리는 것, 외우는 법은 비유와 요령, 출제 예상은 질문으로 나올 만한 것입니다. 바이트 값은 이번 주에 직접 만든 데모 서버(ws-demo)에서 찍은 실제 값입니다(11/23). 30분이면 됩니다.

UNIT 1 · 바탕

준비: HTTP는 묻고 답하면 끝이다

HTTP에서는 브라우저가 물어야 서버가 답한다. 서버는 물어보지 않은 것을 먼저 보낼 수 없다.

지금까지 배운 HTTP의 모양

1~4주차에 본 HTTP는 언제나 같은 모양이었습니다. 브라우저(클라이언트)가 요청을 보내고, 서버가 응답을 하나 돌려주면 그 한 번의 대화가 끝납니다. 요청 하나에 응답 하나, 그리고 시작은 언제나 브라우저입니다.

브라우저서버
① 묻는다GET /messages
200 OK · 새 메시지 없음② 답한다. 끝
… 3초 뒤 친구가 메시지를 보냄. 서버는 알지만 브라우저에 알릴 길이 없다 …
③ 다시 물어야GET /messages
200 OK · 새 메시지 1개④ 그제야 전달

채팅이나 알림처럼 서버 쪽에서 먼저 일이 생기는 기능은 이 모양과 맞지 않습니다. 서버는 새 메시지가 왔다는 걸 알아도, 브라우저가 다시 묻기 전까지 전할 방법이 없습니다.

외우는 법 · 무전기와 전화

HTTP는 무전기입니다. 한 사람이 "오버" 하고 말을 마쳐야 상대가 답하고, 묻지 않으면 답도 없습니다. WebSocket은 전화입니다. 한 번 걸어 두면 둘 다 아무 때나 말할 수 있습니다.

그런데 선(TCP)은 원래 양방향이다

HTTP 아래에는 2주차에 본 TCP 연결이 있습니다. TCP 연결은 양쪽이 아무 때나 바이트를 보낼 수 있는 양방향 통로입니다. "브라우저가 묻고 서버가 답한다"는 건 TCP의 한계가 아니라 HTTP라는 대화 규칙의 한계입니다. WebSocket은 이 점을 이용합니다. TCP 연결은 그대로 두고, 그 위의 대화 규칙만 바꿉니다.

함정

"서버가 먼저 브라우저에 연결하면 되잖아?"는 안 됩니다. 1주차에 본 것처럼 브라우저는 대개 공유기(NAT) 뒤에 있어서, 바깥에서 먼저 건 연결은 어느 기기로 보낼지 모릅니다. 그래서 실시간 기술은 모두 브라우저가 먼저 연결을 열고, 서버가 그 길로 보내는 구조입니다. WebSocket도 시작은 브라우저입니다.

오늘 나오는 헤더·메시지는 누가 보내나

오늘 공부의 절반은 이 표입니다. 핸드셰이크(단원 3)는 HTTP 요청·응답 한 쌍이라 지난주처럼 "요청에 싣는 것"과 "응답에 싣는 것"이 나뉩니다. 연결 뒤의 프레임(단원 4~6)은 양쪽 다 보냅니다.

Key는 묻는 쪽(브라우저)이 내는 문제, Accept는 답하는 쪽(서버)이 내는 정답입니다. Protocol·Extensions는 브라우저가 목록을 내밀고 서버가 골라서 돌려줍니다. 지난주 Accept-Language(요청)와 이름이 닮았지만 Sec-WebSocket-Accept는 응답 헤더입니다.

UNIT 2

WebSocket이 뭔가: 한 번 연결하고 계속 쓰는 양방향 통로

WebSocket은 HTTP로 인사한 뒤 같은 TCP 연결을 계속 열어 두고, 브라우저와 서버가 아무 때나 서로 메시지를 보내는 규칙이다.

정의를 세 조각으로

  1. HTTP로 시작한다: 처음 한 번은 보통 HTTP 요청처럼 보냅니다. 그래서 80·443 포트, 기존 서버·프록시를 그대로 지날 수 있습니다. 단원 3.
  2. 연결을 끊지 않는다: 인사가 끝나도 TCP 연결을 계속 씁니다. 메시지마다 새로 연결하거나 헤더를 다시 보내지 않습니다.
  3. 양쪽이 아무 때나 보낸다: 브라우저도 서버도 상대가 묻지 않아도 메시지를 보냅니다. 메시지는 프레임이라는 작은 꾸러미에 담깁니다. 단원 4.

규칙의 정식 이름은 RFC 6455(2011)입니다. RFC는 인터넷 기술의 공식 설명서이고, 숫자는 문서 번호입니다. 주소는 ws://(암호화 없음, 기본 80번 포트)와 wss://(TLS로 암호화, 기본 443번)로 씁니다. http://와 https://의 짝이라고 보면 됩니다.

왜 필요한가

  • 서버가 먼저 말할 수 있다: 새 채팅 메시지, 주문 상태 변경, 다른 사람의 커서 위치를 생기는 즉시 보냅니다.
  • 짧은 메시지가 가볍다: HTTP 요청 하나에는 헤더만 수백 바이트(쿠키가 있으면 더)가 붙습니다. WebSocket 프레임의 머리는 2~14바이트입니다. "Hi" 두 글자를 서버가 보내면 선 위에는 4바이트가 지나갑니다.
  • 양방향이 잦은 일에 맞다: 채팅, 게임, 공동 편집처럼 양쪽이 쉴 새 없이 주고받는 경우.

대신 생기는 문제

공짜는 아닙니다. HTTP가 알아서 해 주던 일을 이제 직접 챙겨야 합니다.

  • 연결을 계속 붙잡는다: 사용자 만 명이면 서버에 열린 연결도 만 개입니다. 서버를 여러 대 두면 "이 사용자는 몇 번 서버에 붙어 있지?"를 알아야 합니다(7주차 Redis).
  • 중간 장비가 끊는다: 프록시·로드밸런서는 말 없는 연결을 정리합니다. 살아 있다는 신호(ping)를 직접 보내야 합니다. 단원 6, 6주차.
  • HTTP의 편의가 없다: 메시지마다 상태 코드도, 캐시도, 자동 재연결도 없습니다. 끊기면 다시 붙는 코드도 직접 씁니다. 단원 8.
쪽집게 · 세 방식 한 줄 비교

서버가 먼저 보내는 방법은 셋입니다(자세한 건 이주영님 발표). 롱 폴링은 "새 소식 생길 때까지 답을 미루는 HTTP", SSE는 "서버 → 브라우저 한 방향으로 계속 흘리는 HTTP 응답", WebSocket은 "HTTP에서 갈아탄 양방향 통로"입니다. 알림만 내려보내면 SSE로 충분하고, 양쪽이 자주 말하면 WebSocket입니다.

SSE한 방향 · 그대로 HTTP

평범한 HTTP 응답을 끝내지 않고 이어 씁니다. 글자만, 서버 → 브라우저만. 끊기면 브라우저(EventSource)가 알아서 다시 연결합니다.

WebSocket양방향 · HTTP에서 갈아탐

101 뒤로는 HTTP가 아닙니다. 글자와 바이너리, 양쪽 다. 끊기면 다시 연결은 내 코드 몫입니다.

함정

"실시간이면 무조건 WebSocket"이 아닙니다. 진단 퀴즈 Q33처럼 알림만 내려보내고 사용자 행동은 가끔 일반 API로 보내는 화면이면 SSE가 더 단순합니다. WebSocket은 연결 관리, 재연결, 인증을 다 직접 해야 합니다.

UNIT 3 · Q32

연결 시작: Upgrade 요청 → 101 Switching Protocols

브라우저가 Upgrade: websocket을 붙인 HTTP 요청을 보내고, 서버가 101 Switching Protocols로 답하면, 같은 TCP 연결에서 그때부터 WebSocket 프레임이 오간다.

진단 퀴즈 Q32

출제 예상 · Q32
QWebSocket 연결은 어떻게 시작되나요? AHTTP 요청에 Upgrade: websocket 헤더를 붙여 보내고, 서버가 101 Switching Protocols로 응답하면 같은 TCP 연결에서 양방향 프레임을 주고받는다. 별도 포트로 처음부터 따로 연결하는 게 아니고, 서버가 먼저 거는 것도 아닙니다.

실제 모습: 데모 서버에서 찍은 핸드셰이크 (11/23)

GET /ws HTTP/1.1                                 ← 요청 (브라우저 → 서버). 평범한 GET
Host: localhost:8081
Upgrade: websocket                               ← "WebSocket으로 바꾸자"
Connection: Upgrade                              ← "Upgrade는 이 연결 얘기"
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==      ← 브라우저가 낸 문제 (무작위)
Sec-WebSocket-Version: 13

HTTP/1.1 101 Switching Protocols                 ← 응답 (서버 → 브라우저). 마지막 HTTP
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=  ← 서버가 계산한 정답
                                                 ← 빈 줄. 여기부터 HTTP가 아니라 프레임

응답에 본문이 없습니다. 빈 줄 다음부터 오는 바이트는 HTTP 본문이 아니라 WebSocket 프레임입니다. 같은 TCP 연결이 그대로 이어지고, 그 위의 대화 규칙만 바뀌었습니다.

브라우저서버
⓪ TCP 연결SYN → SYN+ACK → ACK
① HTTP로 인사GET /ws · Upgrade: websocket · Key
101 Switching Protocols · Accept② 갈아타기 승낙
… 같은 TCP 연결. 이제부터 HTTP가 아니다 …
③ 아무 때나프레임: "Hi"
프레임: "#1: Hi"④ 서버도 아무 때나
프레임: "[서버] 공지"⑤ 묻지 않았는데 보냄

Key와 Accept: 문제와 정답

서버는 받은 키 뒤에 RFC에 박혀 있는 고정 문자열 258EAFA5-E914-47DA-95CA-C5AB0DC85B11을 붙이고, SHA-1 해시를 낸 뒤 base64로 바꿔 돌려줍니다. 해시는 "아무 길이의 글을 넣으면 정해진 길이의 지문이 나오는 계산"이고, base64는 바이트를 글자로 옮겨 적는 방법입니다.

Accept = base64( SHA-1( Key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11" ) )

$ printf '%s' 'dGhlIHNhbXBsZSBub25jZQ==258EAFA5-E914-47DA-95CA-C5AB0DC85B11' \
    | openssl sha1 -binary | base64
s3pPLMBiTxaQ9kYGzzhZRbK+xOo=          ← RFC 6455 1.3절의 예와 똑같다

브라우저는 101을 받으면 이 값을 스스로 계산해 맞춰 봅니다. 틀리면 연결을 버립니다.

함정 · Key는 보안 장치가 아니다

Key·Accept는 비밀번호도 암호화도 아닙니다. 계산법이 공개되어 있어 누구나 맞힐 수 있습니다. 목적은 "상대가 WebSocket을 진짜 이해하는 서버인지" 확인하는 것입니다. WebSocket을 모르는 보통 HTTP 서버나 캐시가 옛 응답을 엉뚱하게 돌려줘도, 그 응답엔 맞는 Accept가 없으니 브라우저가 속지 않습니다. 인증은 따로 합니다(7주차).

왜 굳이 HTTP로 시작하나

  • 같은 문으로 들어간다: 회사 방화벽은 대개 80·443만 열어 둡니다. HTTP처럼 시작하면 웹과 같은 포트, 같은 서버(nginx 등)를 씁니다.
  • HTTP가 해 놓은 걸 쓴다: 주소(URL), 쿠키, TLS(wss://)가 그대로 따라옵니다. 브라우저는 그 사이트의 쿠키를 핸드셰이크 요청에 실어 보냅니다.
쪽집게 · 갈아타기 승낙은 101 하나뿐

성공은 101뿐입니다. 200이 오면 실패입니다. 서버가 싫다고 할 때는 보통 HTTP 오류로 답합니다. 데모 서버 기준(11/23): 버전이 13이 아니면 426 Upgrade Required + Sec-WebSocket-Version: 13, 헤더가 빠지면 400, 허락하지 않는 출처면 403. 이때 브라우저 JS에는 자세한 이유 없이 error와 close(코드 1006)만 옵니다.

하위 프로토콜과 확장: 목록을 내밀고 하나 고르기

지난주 콘텐츠 협상(Accept-* → Content-*)과 같은 모양입니다. 브라우저가 new WebSocket(url, ['demo.v1'])처럼 후보를 주면 요청에 Sec-WebSocket-Protocol: demo.v1이 실리고, 서버가 그중 하나를 응답에 적어 고릅니다. 압축 같은 덧붙임 기능은 Sec-WebSocket-Extensions로 같은 식으로 고릅니다.

출제 예상 · 실측
QNode 24의 WebSocket이 핸드셰이크에 Sec-WebSocket-Extensions: permessage-deflate; client_max_window_bits를 실어 보냈다. 데모 서버는 응답에 이 헤더를 안 넣었다. 압축이 될까? A안 된다. 확장은 브라우저가 제안하고 서버가 응답에 적어야 켜집니다. 응답에 없으면 압축 없이 주고받습니다. 제안만으로는 아무것도 안 바뀝니다.

UNIT 4

연결 뒤에 오가는 것: 프레임

101 뒤로는 프레임만 오간다. 프레임은 2바이트 머리(끝났나, 종류, 가면, 길이)와 내용으로 되어 있고, 메시지 하나는 프레임 하나 이상이다.

메시지와 프레임

내 코드에서 ws.send("Hi")로 보내는 단위가 메시지입니다. 선 위에서는 그 메시지가 프레임(frame)이라는 꾸러미에 담겨 갑니다. 보통은 메시지 하나 = 프레임 하나이고, 아주 큰 메시지는 프레임 여러 개로 쪼개 보낼 수 있습니다(조각내기). 받는 쪽 브라우저는 조각을 다 모아 message 이벤트 한 번으로 줍니다.

외우는 법 · 편지와 봉투

메시지는 편지, 프레임은 봉투입니다. 봉투 겉면(머리)에 "이게 마지막 장인지, 글인지 사진인지, 몇 바이트인지"를 적습니다. 긴 편지는 봉투 여러 개에 나눠 넣고, 마지막 봉투에만 "끝"(FIN) 표시를 합니다.

머리 2바이트에 든 것

출제 예상 · 계산
Q서버가 1,000바이트짜리 글 메시지를 마스크 없이 보낸다. 프레임 머리는 몇 바이트이고 두 번째 바이트 값은? A4바이트, 두 번째 바이트는 126(0x7e). 1,000은 125보다 크고 65,535 이하라서, 길이 칸에 126을 적고 뒤 2바이트(03 e8)에 진짜 길이를 씁니다. 데모의 150바이트 한글 메시지도 81 fe 00 96(마스크 있음: fe = 1 + 126)으로 찍혔습니다. Q"Hi"를 브라우저가 보낼 때와 서버가 보낼 때 머리 크기는? A브라우저 6바이트, 서버 2바이트. 브라우저가 보낸 프레임에는 마스크 키 4바이트가 붙습니다.
함정 · TCP는 프레임 경계를 모른다

TCP는 바이트를 순서대로 나를 뿐, "여기까지가 한 프레임"을 모릅니다. 프레임 하나가 두 번에 나뉘어 도착하거나, 두 프레임이 한 번에 붙어 올 수 있습니다. 그래서 받는 쪽은 길이 칸을 보고 "다 왔나"를 직접 셉니다. 데모 서버의 decodeFrame이 덜 왔으면 null을 돌려주고 기다리는 이유입니다.

쪽집게

text 프레임의 내용은 UTF-8로 맞는 글자여야 합니다. 깨진 바이트가 오면 받는 쪽은 close 코드 1007로 끊습니다. 글자가 아닌 데이터는 binary(0x2)로 보냅니다.

UNIT 5

클라이언트만 쓰는 가면: 마스킹

브라우저 → 서버 프레임은 매번 무작위 4바이트 키로 가면을 씌우고, 서버 → 브라우저 프레임은 씌우지 않는다. 가면은 비밀 유지가 아니라 중간 장비를 속이지 않으려고 쓴다.

어떻게 씌우나

브라우저는 프레임마다 새 마스크 키 4바이트를 무작위로 고르고, 내용의 각 바이트를 키와 차례로 XOR합니다. XOR은 "같은 값으로 두 번 하면 원래대로 돌아오는" 비트 계산이라, 서버는 같은 키로 한 번 더 XOR해서 벗깁니다. 키는 프레임 머리에 그대로 적혀 갑니다.

내용 i번째 바이트  ⊕  키[i % 4]   = 가면 쓴 바이트
'H' 48            ⊕  33          = 7b
'i' 69            ⊕  bf          = d6
받는 쪽:  7b ⊕ 33 = 48 'H'   (같은 키로 한 번 더 → 원래대로)

왜 쓰나: 엉뚱한 캐시가 속지 않게

WebSocket이 나오던 무렵, 연구자들이 이런 공격을 보였습니다. 공격자 웹페이지가 브라우저를 시켜 HTTP 요청처럼 보이는 바이트를 WebSocket(정확히는 그 시험판)으로 보내게 하면, WebSocket을 모르는 오래된 투명 프록시가 그걸 진짜 HTTP 요청으로 착각해 가짜 응답을 캐시에 저장할 수 있었습니다. 그 뒤로 같은 프록시를 쓰는 다른 사람이 오염된 응답을 받게 됩니다(캐시 오염, 지난주 공용 캐시 이야기).

마스킹을 하면 브라우저가 실제로 선에 내보내는 바이트를 페이지의 JavaScript가 고를 수 없습니다. 키가 매번 무작위라 "HTTP처럼 보이는 바이트"를 일부러 만들 수 없게 됩니다.

브라우저 → 서버반드시 가면 (MASK=1)

서버는 가면 없는 프레임을 받으면 연결을 끊습니다. 데모 서버는 close 코드 1002(규칙 위반)로 끊습니다(시험으로 확인).

서버 → 브라우저가면 없음 (MASK=0)

공격 바이트를 만들 수 있는 건 남의 페이지가 시키는 브라우저 쪽이라, 서버 쪽은 씌울 필요가 없습니다. 씌우면 오히려 브라우저가 끊습니다.

함정 · 마스킹은 암호화가 아니다

키가 프레임 머리에 그대로 적혀 가니, 선을 엿보는 사람은 누구나 벗길 수 있습니다. 와이어샤크로 ws://를 잡으면 내용이 다 보입니다. 내용을 숨기려면 wss://(TLS)를 씁니다. 실서비스는 언제나 wss://입니다.

외우는 법 · 클라이언트가 가면(Client Masks)

"Client Masks"로 외우세요. 가면을 쓰는 쪽은 남의 페이지가 시킬 수 있는 쪽(클라이언트)입니다. 서버는 맨얼굴입니다.

출제 예상
Q마스킹 키가 프레임 안에 그대로 있으면 무슨 소용인가? A숨기는 게 목적이 아니라 예측할 수 없게 하는 게 목적입니다. 페이지의 JS가 선 위의 바이트를 마음대로 정하지 못하게 해서, WebSocket을 모르는 중간 장비가 그 바이트를 HTTP로 착각하는 일을 막습니다.

UNIT 6

살아 있니, 그만하자: ping·pong·close

ping을 받으면 같은 내용으로 pong을 돌려준다. 끝낼 때는 close 프레임을 주고받은 뒤 TCP를 닫고, close에는 이유를 말하는 숫자 코드가 붙는다.

ping과 pong: "살아 있니?" "응"

메시지가 한동안 없으면 연결이 살아 있는지 알 수 없습니다. 상대 컴퓨터가 꺼졌어도 TCP는 한참 동안 모를 수 있습니다. 그래서 한쪽이 ping(0x9)을 보내면 받은 쪽은 같은 내용으로 pong(0xA)을 돌려줍니다. 이걸 주기적으로 하는 것을 하트비트(heartbeat, 심장 박동)라고 합니다.

→ 서버 → 브라우저   89 0d 31 37 39 35 …    ping  "1795424013249" (보낸 시각)
← 브라우저 → 서버   8a 8d 34 b9 47 1d …    pong  같은 내용 (가면 씀)
   pong까지 1ms                            ← 데모 서버, 11/23

하트비트는 두 가지 일을 합니다. ① 죽은 연결 찾기: 데모 서버는 15초마다 ping을 보내고, 다음 차례까지 pong이 없으면 연결을 끊습니다. ② 중간 장비 깨우기: 프록시·로드밸런서는 말 없는 연결을 일정 시간(흔히 60초 안팎) 뒤 끊습니다. 그보다 자주 ping이 지나가면 끊기지 않습니다. 6주차 주제입니다.

함정 · 브라우저 JS는 ping을 못 보낸다

브라우저는 서버의 ping에 pong을 알아서 답하지만, 브라우저 WebSocket API에는 ping을 보내는 함수가 없습니다. 그래서 브라우저 쪽에서 살아 있는지 확인하려면 ws.send('{"type":"ping"}')처럼 보통 메시지로 직접 만듭니다. "서버가 ping, 브라우저는 자동 pong"이 기본입니다.

쪽집게 · 제어 프레임 규칙

ping·pong·close는 내용이 125바이트 이하이고 쪼갤 수 없습니다. 대신 긴 메시지가 조각나 오는 사이에 끼어들 수 있습니다. 큰 파일을 보내는 중에도 하트비트가 막히지 않게 하려는 규칙입니다.

close: 인사하고 헤어지기

끝낼 때는 TCP를 그냥 끊지 않고, 먼저 close 프레임(0x8)을 보냅니다. 받은 쪽도 close 프레임으로 답하고, 그다음 TCP 연결을 닫습니다. close 내용의 앞 2바이트는 이유 코드, 나머지는 짧은 설명 글입니다.

함정 · 1006은 아무도 보내지 않았다

로그에 close code=1006이 찍히면 "서버가 1006을 보냈다"가 아닙니다. close 프레임 없이 연결이 끊겼다는 뜻입니다. 프록시 유휴 타임아웃, 서버 강제 종료, 네트워크 끊김, 핸드셰이크 실패가 흔한 원인입니다. 1005(코드 없이 닫음)도 같은 "알림 전용" 값입니다.

외우는 법

1000은 "잘 가", 1001은 "나 간다", 1006은 "전화가 그냥 끊겼다". 1006은 상대가 한 말이 아니라 내가 겪은 일입니다.

UNIT 7

브라우저에서 쓰고 눈으로 보기

브라우저에서는 new WebSocket(url) 한 줄로 핸드셰이크가 시작되고, open·message·error·close 네 이벤트로 일이 일어난다. DevTools Network의 WS 줄 하나에서 101과 메시지를 다 볼 수 있다.

코드 한 덩어리

const ws = new WebSocket('wss://example.com/ws', ['demo.v1']);  // 여기서 핸드셰이크 시작
ws.onopen    = () => ws.send('Hi');               // 101을 받은 뒤. 이 전에 send하면 오류
ws.onmessage = (e) => console.log(e.data);        // 서버가 보낸 메시지 (글자면 string)
ws.onerror   = () => console.log('문제 생김');      // 이유는 안 알려 준다
ws.onclose   = (e) => console.log(e.code, e.reason, e.wasClean);
ws.close(1000, 'bye');                            // 정중하게 끝내기
readyState뜻
0 CONNECTING핸드셰이크 중. 아직 send 못 함
1 OPEN101을 받았다. 주고받을 수 있음
2 CLOSINGclose를 보냈고 답을 기다림
3 CLOSED끝. 다시 쓰려면 새 WebSocket을 만든다
  • binaryType: 바이너리 메시지를 Blob(기본)으로 받을지 ArrayBuffer로 받을지.
  • bufferedAmount: send했지만 아직 선으로 못 나간 바이트 수. 너무 빨리 보내고 있는지 보는 값.
  • protocol: 서버가 고른 하위 프로토콜(데모에서는 "demo.v1").
함정 · 헤더를 마음대로 못 붙인다

브라우저 WebSocket API에는 요청 헤더를 넣는 칸이 없습니다. fetch처럼 Authorization: Bearer …를 붙일 수 없습니다. 브라우저가 알아서 붙이는 건 쿠키와 Origin, 내가 고를 수 있는 건 하위 프로토콜 목록뿐입니다. 그래서 인증은 쿠키, 주소의 토큰, 연결 직후 첫 메시지 중에서 고릅니다. 7주차 이주영님 주제입니다.

함정 · 저절로 다시 붙지 않는다

SSE의 EventSource는 끊기면 알아서 다시 연결하지만, WebSocket은 한 번 CLOSED면 끝입니다. 다시 붙는 코드(기다렸다 새로 new WebSocket, 기다리는 시간은 점점 늘리기)는 직접 씁니다.

DevTools로 보기

  1. F12 → Network 탭을 연 채로 페이지를 새로 엽니다(연결 전에 열어 둬야 잡힙니다).
  2. 필터에서 WS(Chrome 버전에 따라 Socket)를 누르면 WebSocket 줄만 남습니다.
  3. 그 줄을 누르면 Headers에 101 요청·응답 헤더, Messages에 오간 메시지가 시간순으로 나옵니다. 위쪽 화살표(보낸 것)와 아래쪽 화살표(받은 것)로 방향을 구분합니다.
쪽집게 · 실측

WebSocket은 Network 탭에 줄이 하나만 생깁니다. 메시지를 백 번 주고받아도 요청 줄은 늘지 않습니다. 폴링이면 묻는 횟수만큼 줄이 쌓입니다. "1분 동안 HTTP 요청 수"를 비교하면 차이가 바로 보입니다(과제 E 체크 항목).

출제 예상 · 발표 뒤 질문
QNetwork 탭에 WebSocket 줄의 상태가 계속 "Pending"이고 시간이 늘어나요. 문제인가요? A정상입니다. 101 이후 연결을 계속 쓰고 있어서 "끝나지 않은 요청"으로 보입니다. 상태 열에 101이 찍혀 있으면 핸드셰이크는 성공한 것입니다.

UNIT 8

실무에서는: 프록시, 재연결, 서버 여러 대

WebSocket이 운영에서 깨지는 곳은 대개 가운데 장비다. 프록시가 Upgrade를 넘겨줘야 연결되고, ping이 지나가야 안 끊기고, 끊기면 다시 붙는 코드는 내가 쓴다.

프록시가 Upgrade를 넘겨줘야 한다

Upgrade와 Connection은 "바로 옆 한 구간에만 해당하는" 헤더(hop-by-hop 헤더)라서, nginx 같은 리버스 프록시는 기본으로 다음 서버에 넘기지 않습니다. 그러면 앱 서버는 평범한 GET만 받고 101을 못 줍니다. nginx에서는 이렇게 넘깁니다.

location /ws {
    proxy_pass http://app:8081;
    proxy_http_version 1.1;                    # Upgrade는 HTTP/1.1의 기능
    proxy_set_header Upgrade $http_upgrade;    # 받은 Upgrade를 그대로 넘김
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 75s;                    # 이 시간 동안 말이 없으면 끊음 (기본 60s)
}

실제로 공개 에코 서버 echo.websocket.org에 핸드셰이크를 보내 보면(11/23), 101 응답에 via: 1.1 fly.io, 1.1 fly.io가 붙어 옵니다. 프록시 두 대를 지나서도 Upgrade가 잘 전달되어 연결된 것입니다.

함정 · 1~2분 뒤 끊기는 연결 (Q35)

"아무 메시지 없이 1분쯤 지나면 끊겨요"는 WebSocket의 제한이 아니라 가운데 장비의 유휴 타임아웃입니다(nginx proxy_read_timeout 기본 60초, 클라우드 로드밸런서도 비슷). 해결은 그보다 짧은 간격의 ping(하트비트)과 재연결입니다. 6주차에 직접 재현합니다.

재연결: 점점 늦게, 조금씩 다르게

서버를 배포하면 붙어 있던 사용자가 한꺼번에 끊기고, 한꺼번에 다시 붙으려 합니다. 모두 같은 순간에 재시도하면 서버가 다시 쓰러집니다. 그래서 기다리는 시간을 1초, 2초, 4초…로 늘리고(지수 백오프), 사람마다 조금씩 흩뜨립니다(지터). 3주차 재시도 이야기와 같은 원리입니다.

서버가 여러 대면

사용자 A는 1번 서버에, B는 2번 서버에 붙어 있으면, A가 보낸 메시지를 B에게 전하려면 서버끼리 알려 주는 길이 필요합니다. 흔히 Redis pub/sub(한 서버가 "발행"하면 구독한 모든 서버가 받는 방송)을 씁니다. 7주차 과제 F입니다.

HTTP/2·3에서는?

지금까지 본 Upgrade 방식은 HTTP/1.1의 기능입니다. HTTP/2는 연결 하나에 여러 요청을 섞어 보내서(4주차 멀티플렉싱) "이 연결을 통째로 바꾸자"가 안 맞습니다. 그래서 HTTP/2·3에서는 스트림 하나를 WebSocket으로 쓰는 방식(RFC 8441, RFC 9220: CONNECT 요청 + :protocol: websocket, 성공은 101이 아니라 200)이 따로 있습니다. 브라우저와 서버가 둘 다 지원할 때만 쓰이고, 지원이 아직 고르지 않습니다. "기본은 HTTP/1.1 Upgrade"로 알아 두면 됩니다.

쪽집게 · 운영 체크 다섯

① wss://만 쓴다 ② 프록시에 Upgrade·Connection 전달 ③ 유휴 타임아웃보다 짧은 ping ④ 끊기면 백오프 재연결 ⑤ 핸드셰이크 때 Origin과 로그인 확인(7주차).

출제 예상 · 발표 뒤 질문
Q로컬에서는 되는데 nginx 뒤에 두니 연결이 안 되고, 앱 로그엔 보통 GET /ws만 찍혀요. Anginx가 Upgrade·Connection 헤더를 넘기지 않았습니다. proxy_http_version 1.1과 두 proxy_set_header를 넣습니다. 데모 서버는 Upgrade 없이 온 /ws에 426을 돌려주니, 이 상황이면 브라우저가 426을 봅니다. QWebSocket은 CORS 검사를 받나요? A받지 않습니다. 다른 사이트의 페이지도 내 서버에 WebSocket을 열 수 있습니다. 그래서 서버가 핸드셰이크의 Origin을 직접 확인해야 합니다. 7주차 주제입니다.

UNIT 9 · 지난주 과제

지난주 과제 D와 이어지는 곳

과제 D에서 ETag를 붙여 "안 바뀌었으면 304, 본문 없음"을 확인했다. 그 모든 건 묻고 답하는 HTTP 안의 이야기이고, 오늘은 묻지 않아도 서버가 보내는 쪽으로 넘어간다.

과제 D에서 한 일 (11/23, nginx 뒤에서)

GET /orders/1                              → 200  본문 71바이트  ETag: "ff40bac14f087c63efe2"
GET /orders/1  If-None-Match: "ff40…"      → 304  본문 0바이트   (ETag·Cache-Control만)
PATCH /orders/1  If-Match: "ff40…" qty=3   → 200  ETag가 "5a8c…"로 바뀜
GET /orders/1  If-None-Match: "ff40…"(옛것) → 200  새 본문
PATCH /orders/1  If-Match: "ff40…"(옛것)    → 412  주문은 그대로 (남이 먼저 고쳤다)
  • 주문은 사람마다 다르니 Cache-Control: private, no-cache: 브라우저만 저장하고, 쓸 때마다 ETag로 묻습니다.
  • nginx에서 gzip을 켜면 ETag가 W/"…"(약한 ETag)로 바뀌었습니다. 304는 여전히 오지만(If-None-Match는 약하게 비교), If-Match는 강하게 비교해서 그 값으로는 412가 납니다.
  • 사이트 프로토콜: 네이버·GitHub·MDN·jQuery 문서는 모두 h2. GitHub 정적 파일 서버에서는 같은 페이지 안에서도 h2와 h3가 섞여 나왔습니다. 다른 출처 파일은 서버가 Timing-Allow-Origin을 안 주면 Protocol 값을 읽을 수 없었습니다.
쪽집게 · 다리

캐시와 ETag는 "브라우저가 물을 때 덜 보내는 법"이었습니다. WebSocket은 "브라우저가 묻지 않아도 보내는 법"입니다. 둘 다 같은 질문, "필요한 만큼만 주고받으려면?"에 대한 답입니다.

함정

WebSocket 메시지에는 ETag도 Cache-Control도 없습니다. 101 뒤로는 HTTP가 아니라서, 지난주에 배운 캐시 규칙은 핸드셰이크 요청에만 해당하고(그것도 저장하지 않습니다) 메시지에는 전혀 적용되지 않습니다. 같은 걸 또 보내지 않는 건 내 앱이 정할 일입니다.

  1. HTTP는 브라우저가 물어야 서버가 답한다. WebSocket은 한 번 연결해 두고 양쪽이 아무 때나 보낸다.

  5. ping엔 pong, 끝낼 땐 close 코드(1000 정상). 1006은 close 없이 끊긴 것이고, 끊기면 다시 붙는 건 내 몫이다.
