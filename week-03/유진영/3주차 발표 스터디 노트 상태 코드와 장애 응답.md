# 3주차 발표 스터디 노트: 상태 코드와 장애 응답

2026-11-03 · 유진영


## 비유 사전

이번 노트는 "건물 안내 데스크" 비유를 계속 씁니다.

| 비유 | 실제 이름 | 뜻 |
| --- | --- | --- |
| 손님 | 브라우저, 앱 (클라이언트) | 요청을 보내는 쪽 |
| 안내 데스크 | 리버스 프록시 (nginx, 로드 밸런서) | 손님 요청을 대신 받아 안쪽 담당자에게 넘기는 서버 |
| 안쪽 담당자 | 앱 서버 (업스트림) | 실제로 일을 처리하는 우리 코드 |
| 처리 결과 도장 | 상태 코드 | 응답 첫 줄의 세 자리 숫자 |
| 담당자에게 건 내선 전화 | 프록시 → 앱 TCP 연결 | 1주차에 본 그 연결 |

## 먼저 알아 둘 배경 지식 (장표 2~4)

상태 코드는 외우는 게 아니라 "누가, 왜 이 숫자를 찍었나"를 읽는 겁니다. 그러려면 아래 세 가지를 먼저 알아야 합니다.

### 장표 2 · 응답의 첫 줄에 세 자리 숫자가 있다

**한 줄로**: 서버는 응답 첫 줄에 "처리 결과"를 숫자 하나로 먼저 적어 보낸다.

HTTP는 요청 하나에 응답 하나가 돌아오는 구조입니다. 응답의 맨 첫 줄을 상태 줄이라고 부르고, `HTTP/1.1 404 Not Found`처럼 버전, 숫자, 짧은 문구가 들어갑니다.

- 택배 송장에 찍히는 "배송 완료 / 주소 불명 / 반송" 도장과 같습니다. 상자(본문)를 열기 전에 결과를 압니다.
- 프론트엔드의 `fetch`는 이 숫자를 `res.status`로, 200~299인지를 `res.ok`로 알려 줍니다. 주의할 점은 `fetch`가 404나 500을 받아도 예외를 던지지 않는다는 겁니다. 예외는 연결 자체가 안 됐을 때만 납니다. 그래서 `res.ok`를 직접 확인해야 합니다.
- 뒤의 영어 문구(Not Found)는 사람용 설명이라 코드에서 쓰지 않습니다. HTTP/2는 아예 숫자만 보냅니다.

**이런 질문을 받으면**

- *axios는 4xx·5xx에서 에러를 던지던데?* axios는 기본 설정이 2xx 밖이면 에러로 바꿔 줍니다. `fetch`는 안 바꿔 줍니다. 라이브러리 차이일 뿐 HTTP는 같습니다.

### 장표 3 · 첫 자리만 보면 반이 갈린다

**한 줄로**: 1xx 진행 중, 2xx 성공, 3xx 다른 데로, 4xx 요청 잘못, 5xx 서버가 못 함.

| 반 | 뜻 | 자주 보는 예 |
| --- | --- | --- |
| 1xx | 잠깐, 계속 진행 중 | 101 Switching Protocols (WebSocket으로 갈아탈 때, 5주차) |
| 2xx | 성공 | 200 OK, 201 Created(새로 만들었음), 204 No Content(성공, 본문 없음) |
| 3xx | 다른 데로 가 봐 | 301·302 이동, 304 Not Modified(캐시 그대로 써, 4주차) |
| 4xx | 요청이 잘못됐다 | 400, 401, 403, 404, 409, 422, 429 |
| 5xx | 서버 쪽이 처리 못 했다 | 500, 502, 503, 504 |

- 규칙상 모르는 코드를 받은 클라이언트는 그 반의 x00으로 취급합니다. 499를 받으면 400처럼 다루면 됩니다.
- 참고로 499는 표준 코드가 아니라 nginx가 로그에만 남기는 값으로, "손님이 답을 기다리다 먼저 전화를 끊었다"는 뜻입니다. 브라우저가 페이지를 떠나거나 프론트가 요청을 취소하면 nginx 로그에 499가 찍힙니다.

### 장표 4 · 요청은 여러 층을 거쳐 앱에 닿는다

**한 줄로**: 브라우저가 받은 상태 코드는 앱이 아니라 중간 층이 만든 것일 수 있다.

실서비스에서 브라우저가 우리 앱 서버에 바로 붙는 일은 드뭅니다. 보통 이렇게 갑니다.

```
브라우저 → (CDN) → nginx·로드 밸런서 → 앱 서버 → DB
```

- 리버스 프록시는 건물 안내 데스크입니다. 손님은 안내 데스크하고만 이야기하고, 안내 데스크가 안쪽 담당자에게 내선 전화를 겁니다. HTTPS 해독, 정적 파일, 여러 앱 서버로 나눠 주기 같은 일을 맡습니다. (책 07-1)
- nginx 입장에서 뒤쪽 앱을 **업스트림**(upstream)이라고 부릅니다. nginx 로그에 이 단어가 계속 나옵니다.
- 안내 데스크와 담당자 사이도 1주차에 본 TCP 연결입니다. 이 연결이 거부되거나, 끊기거나, 대답이 늦으면 안내 데스크가 직접 "죄송합니다" 도장을 찍어 손님에게 돌려줍니다. 그게 502·504입니다.

## 4xx: 요청한 쪽이 고쳐야 하는 응답 (장표 5~7)

### 장표 5 · 4xx는 요청 탓, 5xx는 서버 탓

**한 줄로**: 4xx는 같은 요청을 또 보내면 또 실패하고, 5xx는 잠시 뒤 같은 요청이 성공할 수도 있다.

오늘 하나만 기억한다면 이것입니다. 이 구분이 중요한 이유는 대응이 달라서입니다.

- **4xx**: 요청을 고쳐야 합니다. 재시도는 소용없습니다.
- **5xx**: 요청은 문제가 없었을 수 있습니다. 서버가 회복되면 같은 요청이 성공하니 재시도를 고려합니다.
- 모니터링에서도 다르게 봅니다. 5xx 비율이 오르면 우리 장애이고, 4xx 비율이 갑자기 오르면 프론트 배포 실수나 공격(무작위 경로 긁기, 로그인 시도 폭주)을 의심합니다.

### 장표 6 · 자주 쓰는 4xx 일곱 개

**한 줄로**: 400, 401, 403, 404, 409, 422, 429면 실무 대부분이 덮인다.

| 코드 | 한마디로 | 이럴 때 보낸다 |
| --- | --- | --- |
| 400 Bad Request | 못 알아듣겠어 | JSON이 깨졌다, 필수 값이 없다 |
| 401 Unauthorized | 누구세요? | 토큰이 없거나 만료됐다 |
| 403 Forbidden | 누군지 알지만 안 돼 | 일반 사용자가 관리자 API 호출 |
| 404 Not Found | 그런 거 없어 | 없는 주문 번호, 없는 경로 |
| 409 Conflict | 지금 상태랑 부딪혀 | 이미 결제된 주문을 또 결제, 이미 있는 이메일로 가입 |
| 422 Unprocessable Content | 형식은 맞는데 내용이 틀려 | 이메일 형식 오류, 수량이 음수 |
| 429 Too Many Requests | 너무 자주 보냈어 | 요청 한도 초과 |

- 400과 422는 팀마다 기준이 다릅니다. 흔한 방식은 "JSON 자체를 못 읽으면 400, 읽었는데 값 검사에서 걸리면 422"입니다. 어느 쪽이든 팀 안에서 하나로 정하는 게 중요합니다.
- 429는 4xx지만 "잠시 뒤 다시 보내면 되는" 예외적인 코드입니다. (장표 11)

**이런 질문을 받으면**

- *405는?* 405 Method Not Allowed는 그 경로가 해당 메서드를 안 받는다는 뜻입니다(예: GET만 되는데 DELETE). 프레임워크가 알아서 보내 주는 경우가 많아 직접 쓸 일은 적습니다.
- *검색 결과가 0건이면 404?* 아닙니다. "검색은 잘 됐고 결과가 비었다"이니 200에 빈 배열이 맞습니다. 404는 그 주소의 대상 자체가 없을 때입니다.

### 장표 7 · 401과 403은 묻는 질문이 다르다

**한 줄로**: 401은 "너 누구야?"(인증 실패), 403은 "누군지 알아, 근데 안 돼"(권한 없음).

- 401은 신분증 검사에서 걸린 것입니다. 로그인하거나 토큰을 갱신하면 통과할 수 있습니다.
- 403은 신분증은 통과했는데 출입 명단에 없는 것입니다. 다시 로그인해도 결과가 같습니다.
- 이름이 Unauthorized(권한 없음)라 헷갈리지만, 401의 실제 뜻은 "인증 안 됨"입니다. HTTP 초창기에 붙은 이름이 그대로 남은 겁니다.

**섞어 쓰면 생기는 사고**

- 권한이 없는데 401을 보내면: 프론트가 토큰 갱신 → 다시 요청 → 또 401 → 또 갱신… 무한 루프에 빠질 수 있습니다.
- 토큰이 만료됐는데 403을 보내면: 다시 로그인하면 되는 사용자가 "권한 없음" 화면에서 막힙니다.

**이런 질문을 받으면**

- *남의 주문을 조회하면 403? 404?* 둘 다 씁니다. "그 주문이 있다는 사실" 자체를 숨기고 싶으면 404를 보냅니다. 주문 번호가 순서대로 매겨진다면 403은 "그 번호의 주문은 존재한다"는 힌트를 주기 때문입니다.

## 5xx: 누가 만들었고 어디부터 보나 (장표 8~10)

### 장표 8 · 5xx 네 개, 누가 만들었나

**한 줄로**: 500은 앱이, 502·504는 nginx가 만든다. 503은 둘 다 만들 수 있다.

진단 퀴즈 Q17의 답이 이 장표입니다.

| 코드 | 누가 만드나 | 안내 데스크 비유 | 실제로 일어난 일 |
| --- | --- | --- | --- |
| 500 Internal Server Error | 앱 | 담당자가 일하다 "어, 터졌어요" | 처리 중 예외: 코드 버그, DB 쿼리 실패 |
| 502 Bad Gateway | nginx | 내선을 걸었는데 안 받거나, 받자마자 끊김 | 앱에 연결 거부, 앱이 응답 도중 연결을 끊음 |
| 503 Service Unavailable | 앱 또는 nginx·LB | "지금은 접수 안 받습니다" 팻말 | 과부하, 점검 중, 살아 있는 앱 서버가 없음 |
| 504 Gateway Timeout | nginx | 내선은 연결됐는데 한참 대답이 없어 데스크가 끊음 | 앱이 정해진 시간 안에 응답 헤더를 안 보냄 |

- 502와 504는 **앱이 보낸 응답이 아닙니다.** nginx가 대신 써 준 "죄송합니다" 쪽지입니다. 그래서 앱 로그에 아무것도 없는데 브라우저에는 502가 뜨는 일이 생깁니다.
- 504의 "정해진 시간"은 nginx의 `proxy_read_timeout`이고 기본값은 60초입니다. 정확히는 "앱에서 다음 데이터가 오기까지 기다리는 시간"이라, 앱이 처음 응답을 시작하기 전까지 60초 넘게 조용하면 504가 됩니다.
- 502와 504의 차이는 결국 연결이 됐는가입니다. 연결 단계에서 실패하거나 앱이 끊어 버리면 502, 연결은 됐는데 대답이 늦으면 504입니다.

**이런 질문을 받으면**

- *앱에 연결하는 것 자체가 오래 걸리면?* 연결 대기는 `proxy_connect_timeout`(기본 60초)이 따로 있고, 이 시간이 지나면 504가 납니다. 다만 같은 서버나 같은 망 안이라면 연결은 거의 바로 성공하거나 바로 거부되기 때문에, 실무에서 504는 대부분 "응답이 늦은" 경우입니다.
- *CDN이나 로드 밸런서도 502·504를 만드나?* 네. 같은 원리로 자기 뒤쪽이 실패하면 만듭니다. 그래서 "어느 층이 만든 502인가"를 응답 본문의 생김새(nginx 기본 에러 페이지, CDN 에러 페이지)나 `Server` 헤더로 먼저 가려 봅니다.

### 장표 9 · 코드별로 먼저 볼 곳

**한 줄로**: 500은 앱 로그, 502는 앱이 살아 있는지, 504는 앱이 왜 느린지.

| 코드 | 먼저 볼 곳 | nginx error.log에 남는 말 | 흔한 원인 |
| --- | --- | --- | --- |
| 500 | 앱 로그 | (nginx는 조용함) | 스택 트레이스, DB 에러 |
| 502 | 앱 프로세스가 살아 있나 | `connect() failed (111: Connection refused) while connecting to upstream` | 앱이 죽음, 배포 중 재시작, 포트·주소 설정 오류 |
| 502 | 앱이 중간에 끊었나 | `upstream prematurely closed connection while reading response header from upstream` | 앱 크래시, 메모리 부족으로 강제 종료 |
| 503 | 점검·한도 설정 | `no live upstreams while connecting to upstream` | 헬스 체크에서 전부 탈락 |
| 504 | 앱이 왜 느린가 | `upstream timed out (110: Connection timed out) while reading response header from upstream` | 느린 쿼리, 외부 API 응답 대기 |

- 111, 110은 운영체제 오류 번호입니다. 111(ECONNREFUSED)은 1주차 데모에서 서버를 끄고 `nc`로 접속했을 때 본 "연결 거부"와 같은 것입니다. 그 포트에서 듣는 프로세스가 없어서 상대 운영체제가 RST로 돌려보낸 겁니다.
- 504가 잦을 때 `proxy_read_timeout`을 늘리는 건 진통제입니다. 사용자는 더 오래 기다리게 될 뿐이니, 느린 원인(쿼리, 외부 API)을 먼저 줄이고, 정말 오래 걸리는 작업은 "접수했어요(202) → 나중에 결과 확인" 방식으로 바꿉니다.
- 메시지 문구는 nginx 버전에 따라 조금 다를 수 있습니다. 핵심 단어(refused, prematurely closed, timed out)로 찾으면 됩니다.

### 장표 10 · 1주차와 이어진다: 바인딩 실수는 502가 된다

**한 줄로**: 앱 컨테이너가 127.0.0.1에만 귀를 열면 nginx 컨테이너가 붙지 못해 502가 난다.

1주차 발표에서 127.0.0.1은 "나 자신", 0.0.0.0은 "모든 주소에서 받기"라고 했습니다. 이게 docker에서 실제 장애로 이어집니다.

- 컨테이너는 각자 자기만의 127.0.0.1을 가집니다. 앱 컨테이너의 127.0.0.1은 앱 컨테이너 안에서만 통합니다.
- 앱이 `listen 127.0.0.1:3000`이면, nginx 컨테이너가 `http://app:3000`(앱 컨테이너의 IP)으로 접속할 때 그 주소에서 듣는 프로세스가 없습니다. 운영체제가 연결을 거부하고, nginx는 `Connection refused`를 남기고 502를 돌려줍니다.
- 내 노트북에서 `npm start`로 띄워 테스트할 땐 잘 되다가 docker compose로 올리면 502가 나는 대표적인 이유입니다.
- 고치기: 앱을 `0.0.0.0`에 바인딩합니다. 바깥에 공개할지는 compose의 `ports:` 설정과 방화벽으로 따로 정합니다. nginx만 앱에 접근하면 되면 앱의 `ports:`는 아예 빼면 됩니다.

## 클라이언트는 어떻게 대응하고 서버는 어떻게 알려 주나 (장표 11~13)

### 장표 11 · 다시 보내도 되는 응답, 안 되는 응답

**한 줄로**: 429·503은 기다렸다가, 502·504는 조심해서, 4xx는 다시 보내지 않는다. 자동 재시도는 멱등 요청에만.

| 받은 응답 | 재시도? | 어떻게 |
| --- | --- | --- |
| 400, 401, 403, 404, 422 | 아니요 | 요청을 고치거나 사용자에게 알린다. 401만 토큰 갱신 후 한 번 |
| 429, 503 | 예, 기다렸다가 | `Retry-After` 헤더가 있으면 그만큼(초 또는 날짜) 기다린다 |
| 502, 504 | 예, 조심해서 | 간격을 늘려 가며(1초, 2초, 4초…) 몇 번만 |
| 500 | 대개 아니요 | 버그면 몇 번을 보내도 같다 |

**504의 함정**: 504는 "앱이 실패했다"가 아니라 "nginx가 답을 못 들었다"입니다. 앱은 뒤에서 결제를 끝냈을 수도 있습니다. 이때 `POST /payments`를 그대로 다시 보내면 두 번 결제됩니다. 식당에서 주문하고 한참 음식이 안 와서 "주문 안 들어갔나?" 하고 또 주문했더니 두 그릇이 나오는 것과 같습니다.

- 그래서 자동 재시도는 **멱등**(여러 번 해도 결과가 같은) 요청에만 합니다. GET, PUT, DELETE가 멱등입니다.
- POST는 `Idempotency-Key` 헤더처럼 요청마다 고유한 키를 붙이고, 서버가 같은 키로 온 두 번째 요청은 처음 결과를 그대로 돌려줄 때만 재시도합니다. 오늘 주영님 발표(멱등성과 재시도)와 과제 C가 바로 이 내용입니다.
- 간격을 1, 2, 4초로 늘려 가는 걸 지수 백오프라고 합니다. 여기에 약간의 무작위 시간(**지터**)을 섞어서, 장애가 풀리는 순간 모든 클라이언트가 동시에 몰려들지 않게 합니다.

**이런 질문을 받으면**

- *nginx도 스스로 재시도하나?* 네. 업스트림 서버가 여러 대면 `proxy_next_upstream` 설정에 따라 연결 실패 시 다음 서버로 넘깁니다. 다만 요즘 nginx는 POST 같은 멱등이 아닌 요청은 기본으로 다른 서버에 다시 보내지 않습니다. 같은 이유(두 번 처리 위험) 때문입니다.
- *Retry-After는 누가 넣나?* 서버가 넣습니다. 429를 보내는 요청 한도 미들웨어나 점검 중 503 응답에 넣어 주면, 클라이언트가 얼마나 기다려야 할지 알 수 있습니다.

### 장표 12 · 에러 응답은 코드와 본문이 같은 말을 해야 한다

**한 줄로**: 실패인데 200을 보내지 말고, 상태 코드와 본문의 code·message·requestId로 역할을 나눈다.

```
나쁜 예                          좋은 예
HTTP/1.1 200 OK                  HTTP/1.1 403 Forbidden
{"success": false,               {"code": "NO_PERMISSION",
 "message": "권한 없음"}           "message": "관리자만 볼 수 있습니다",
                                  "requestId": "a1b2c3"}
```

실패인데 200을 보내면 생기는 일:

- 모니터링 대시보드의 에러율이 0으로 보입니다. 장애가 나도 알람이 안 울립니다.
- CDN이나 브라우저가 실패 응답을 성공으로 알고 캐시할 수 있습니다.
- 공용 HTTP 클라이언트의 재시도·에러 처리 규칙이 동작하지 않습니다.

역할 나누기:

- **상태 코드**: 기계(모니터링, 캐시, 재시도 로직)가 읽는 큰 결과
- **code**: 프론트가 분기할 세부 사유. 바뀌지 않는 영문 상수로
- **message**: 사람에게 보여 줄 문장. 바뀌어도 되는 값
- **requestId**: 사용자 문의가 왔을 때 nginx 로그와 앱 로그에서 이 요청 하나를 찾는 열쇠. nginx에서 `$request_id`로 만들어 앱에 헤더로 넘기면 두 로그를 같은 값으로 묶을 수 있습니다.

표준 형식이 필요하면 RFC 9457 Problem Details(`application/problem+json`)를 참고할 수 있습니다.

### 장표 13 · 정리

네 줄을 읽기보다 한 문장으로 묶어 말하면 좋습니다. "4xx는 손님이 고칠 일, 5xx는 우리가 고칠 일이다. 그중 502·504는 앱이 아니라 안내 데스크가 찍은 도장이니, 앱이 살아 있는지와 느린지부터 본다." 그다음 "우리 서비스에서는" 박스를 실제 사례로 채워서 말합니다.

- [ ] 최근 겪은 502·504 한 건을 떠올려 원인을 장표 9의 표에 맞춰 보기
- [ ] 우리 nginx(또는 로드 밸런서)의 `proxy_read_timeout` 값 확인
- [ ] 우리 API 중 실패인데 200을 보내는 곳이 있는지 확인
- [ ] 프론트 HTTP 클라이언트가 어떤 코드에서 자동 재시도하는지 확인

### 과제 B 데모 순서

1. **캡처 보여 주기**: 와이어샤크로 `capture/echo-once.pcap`을 열고 필터 `tcp.port == 9000`. 1초 간격으로 세 장면(연결, hello 주고받기, 종료)이 나뉜 것을 보여 줌
2. **종료가 3개인 이유**: FIN, FIN+ACK, ACK. 원래 4단계인데 받는 쪽이 ACK와 자기 FIN을 한 패킷에 실어 보내서 3개로 보인다
3. **TIME\_WAIT 위치**: `npm run timewait`과 `npm run timewait:server`를 차례로 보여 주며 "먼저 끊은 쪽에 남는다"
4. **keep-alive 측정: `npm run bench` → 끔이 약 2배 느리고, 끔 모드에서 TIME\_WAIT 300개가 서버 쪽**에 쌓인 것을 보여 줌
5. **주영님 질문에 답하기**: "서버 쪽 TIME\_WAIT 615개"는 `Connection: close`일 때 서버가 응답 후 먼저 끊기 때문. 클라이언트가 먼저 끊는 게 아니라는 점이 포인트

### 과제 B에서 받을 만한 질문

- *서버에 TIME\_WAIT가 쌓이면 문제인가?* 수천 개 정도는 괜찮습니다. 서버 쪽 TIME\_WAIT는 상대 포트가 제각각이라 포트가 모자라지 않습니다. 문제가 되는 건 nginx → 앱처럼 같은 목적지로 짧은 연결을 많이 여는 쪽입니다. 그래서 nginx는 `upstream` 블록에 `keepalive`를 켜서 앱과의 연결을 다시 씁니다. 과제 C에서 nginx 설정할 때 같이 보면 좋습니다.
- *루프백인데 왜 2배나 차이 나나?* 왕복 시간은 거의 0이지만, 연결마다 소켓을 만들고 닫는 운영체제 작업과 Node 내부 처리가 매번 듭니다. 인터넷 너머 HTTPS라면 핸드셰이크와 TLS 인사가 더해져 차이가 훨씬 커집니다(주영님 측정 2.6배).
