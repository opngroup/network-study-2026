## 주차별 상세

괄호 안 Q번호는 발표자가 진단 퀴즈에서 틀렸거나 몰랐던 문항입니다. 발표는 그 문항을 설명할 수 있게 되는 것을 목표로 합니다.

### 1주차 · 10/19 · 연결의 기초

책 범위: 01-3 캡슐화, 03-2 사설 IP·NAT·예약 주소, 04-1 포트·NAPT

- **유진영 · 캡슐화와 서버 바인딩** (Q02, Q04): HTTP 메시지가 TCP·IP·이더넷 순서로 감싸지는 과정, 127.0.0.1과 0.0.0.0에 바인딩했을 때의 차이
- **이주영 · 포트와 NAT** (Q06, Q07): 출발지 포트를 OS가 고르는 방식, NAPT 변환 테이블, 서버가 클라이언트에 먼저 연결할 수 없는 이유

**과제 A. TCP 에코 서버** (둘 다)

HTTP 프레임워크 없이 소켓 API만으로 받은 글자를 돌려주는 서버를 만듭니다(Node `net`, Python `socket` 등).

- [ ] 접속한 클라이언트의 IP와 포트를 로그로 남기고, 클라이언트 3개를 동시에 붙였을 때 포트가 각각 다른 것 확인
- [ ] 127.0.0.1과 0.0.0.0으로 바인딩해 다른 기기(휴대폰이나 Docker 밖)에서 접속되는지 비교

### 2주차 · 10/26 · TCP 연결의 일생

책 범위: 04-2 연결 수립·종료·TCP 상태, 04-3 흐름·혼잡 제어 (ARQ 세부는 건너뜀), 06장 와이어샤크

- **유진영 · 흐름 제어와 혼잡 제어** (Q12): 수신자 기준과 네트워크 기준의 차이. 개념만 10분으로 짧게
- **이주영 · 핸드셰이크, 종료, TIME\_WAIT** (Q08): SYN → SYN+ACK → ACK, 연결 종료 절차, 먼저 끊는 쪽에 TIME\_WAIT가 남는 이유

**과제 B. 패킷 캡처와 keep-alive 측정** (둘 다)

- [ ] 과제 A 서버에 접속하는 과정을 와이어샤크로 캡처해 핸드셰이크 패킷 3개와 연결 종료 패킷을 찾아 표시
- [ ] 서버와 클라이언트 중 어느 쪽에 TIME\_WAIT가 남는지 `netstat`으로 확인
- [ ] 간단한 HTTP 서버에 요청 100번을 keep-alive 켜고 끈 두 가지로 보내 걸린 시간 비교

### 3주차 · 11/2 · HTTP 의미론

책 범위: 05-2 메서드·상태 코드, 07-1 리버스 프록시

- **유진영 · 상태 코드와 장애 응답** (Q17): 500·502·503·504가 각각 누구의 문제인지, 자주 쓰는 4xx
- **이주영 · 멱등성과 재시도** (Q15, 둘 다 놓침): PUT과 POST의 차이, 네트워크 오류 뒤 재시도해도 되는 요청, Idempotency-Key 패턴

**과제 C. 멱등 API와 502·504 재현** (둘 다, docker compose 권장)

- [ ] `POST /orders`가 같은 `Idempotency-Key`로 두 번 와도 주문을 한 번만 만들도록 구현
- [ ] nginx를 앞에 두고 앱 서버를 끄면 502, 핸들러에 sleep을 넣고 `proxy_read_timeout`을 짧게 하면 504, 앱이 예외를 던지면 500이 나오는 것을 각각 재현

### 4주차 · 11/9 · 캐시와 HTTP 버전

책 범위: 05-3 헤더·캐시·콘텐츠 협상, 05-2 \[좀 더 알아보기\] HTTP의 발전

- **유진영 · 캐시, ETag, 콘텐츠 협상** (Q20, Q21, Q23): `no-cache`와 `no-store`, ETag → If-None-Match → 304 흐름
- **이주영 · HTTP/1.1 → 2 → 3** (Q25 둘 다 놓침, 유진영 Q24): 멀티플렉싱, HOL 블로킹, QUIC이 UDP를 쓰는 이유

**과제 D. ETag 캐시와 프로토콜 비교** (둘 다, 가벼운 주)

- [ ] 과제 C의 `GET /orders/:id`에 ETag를 붙이고, `curl`로 304가 본문 없이 오는 것 확인
- [ ] 우리 서비스와 자주 쓰는 사이트 3곳의 DevTools Protocol 열(h1·h2·h3)과 Cache-Control 값을 표로 정리

### 5주차 · 11/16 · 실시간 통신 1: 방식

책 범위: 없음. MDN 문서와 RFC 6455 1장으로 공부

- **유진영 · WebSocket 핸드셰이크와 프레임** (Q32): `Upgrade` 헤더와 101 응답, 텍스트·바이너리 프레임, ping·pong, close
- **이주영 · 폴링, 롱 폴링, SSE 고르는 기준** (Q30 둘 다 놓침, Q33, Q36): 세 방식의 동작, 단방향 알림에 SSE가 맞는 이유, HTTP/1.1에서 SSE가 연결 자리를 차지하는 문제

**과제 E. 실시간 알림판** (핵심, 각자 약한 방식을 맡음)

서버에서 알림이 생기면 브라우저에 바로 뜨는 페이지를 만듭니다. 알림은 관리자 버튼이나 타이머로 발생시킵니다.

- [ ] 이주영: 롱 폴링 버전과 SSE(`EventSource`) 버전
- [ ] 유진영: WebSocket 버전. 브라우저에서 서버로 "읽음" 표시를 보내는 양방향 기능까지
- [ ] 각 버전의 DevTools 화면(EventStream 탭, WS 탭)과 1분 동안 오간 HTTP 요청 수와 메시지 수를 README에 기록

### 6주차 · 11/23 · 실시간 통신 2: 운영

책 범위: 07-1 로드 밸런싱·리버스 프록시

- **유진영 · 프록시 버퍼링과 유휴 타임아웃** (Q34, Q35): SSE가 몰려서 도착하는 이유, WebSocket이 1\~2분 뒤 끊기는 이유, nginx 설정과 하트비트
- **이주영 · SSE 재연결과 Last-Event-ID**: 연결이 끊겼을 때 놓친 이벤트를 이어 받는 방법, `retry` 필드. 퀴즈 밖 주제지만 과제 F에 직접 필요합니다

**과제 F. nginx 뒤에서 운영하기** (핵심, 2주, 서로의 코드를 바꿔 맡음)

과제 E의 두 결과물을 하나의 docker compose로 묶고 nginx 뒤에 둡니다. 유진영은 SSE 버전을, 이주영은 WebSocket 버전을 맡아 고칩니다.

- [ ] nginx 기본 설정에서 SSE 버퍼링과 WebSocket 유휴 끊김을 먼저 재현
- [ ] `proxy_buffering`, `Upgrade`·`Connection` 헤더, `proxy_read_timeout` 설정으로 해결
- [ ] 하트비트와 자동 재연결 구현. 서버를 재시작해도 화면이 알아서 복구되는지 확인

### 7주차 · 11/30 · 브라우저 보안

책 범위: 05-3 쿠키. CORS는 MDN 문서

- **유진영 · CORS 프리플라이트와 SameSite** (Q38, Q39): 단순 요청과 프리플라이트 요청의 구분, SameSite Lax·Strict·None
- **이주영 · WebSocket 인증과 Origin 검사**: WebSocket은 CORS의 적용을 받지 않아 서버가 Origin을 직접 확인해야 하는 이유, 핸드셰이크 때 쿠키와 토큰 중 무엇으로 인증할지. CORS에 강한 이주영님이 그 지식을 실시간 통신으로 넓히는 발표입니다

**과제 F 계속: 서버 2대와 인증**

- [ ] 앱 서버를 2대로 늘리고, 한 서버에서 만든 알림이 다른 서버에 붙은 사용자에게도 가도록 Redis pub/sub 연결
- [ ] WebSocket·SSE 연결에 로그인 쿠키 검사를 추가하고, 다른 출처 페이지에서 WebSocket 연결을 시도해 Origin 검사로 거부되는지 확인 (SSE는 브라우저의 CORS 규칙을 따름)
